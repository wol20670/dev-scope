## 왜 필요한가?

팀 목록 화면에 각 팀의 이름과 소속 회원 수를 보여 준다고 해 보자.

```java
List<Team> teams = teamRepository.findAll();
for (Team team : teams) {
    System.out.println(team.getName() + ": " + team.getMembers().size());
}
```

코드에는 쿼리가 한 번만 보이지만, SQL 로그를 켜면 이렇게 나온다.

```sql
select t.id, t.name from team t;                     -- 1번: 팀 10개 조회
select m.* from member m where m.team_id = 1;        -- 팀마다 1번씩
select m.* from member m where m.team_id = 2;
-- ...
select m.* from member m where m.team_id = 10;       -- 총 1 + 10번
```

팀 목록을 가져오는 쿼리 **1번**에, 각 팀의 회원을 가져오는 쿼리가 **N번** 더 실행되었다. 이것이 **N+1 문제**다.

로컬에서 팀 10개일 때는 티가 안 나지만, 운영에서 한 페이지에 100건을 보여 주고 연관이 두세 개 겹치면 요청 하나에 수백 번의 쿼리가 나간다. 쿼리 하나하나는 빠르더라도 DB 왕복(네트워크 지연)이 쌓여 응답이 느려지고, DB 부하도 커진다. JPA가 SQL을 대신 만들어 주기 때문에 **코드만 봐서는 잘 드러나지 않는다**는 점이 이 문제를 더 위험하게 만든다.

## 쉽게 이해하는 비유

**도서관에서 책 정보를 조사**한다고 해 보자.

- N+1 방식: 사서에게 "추천 도서 목록 주세요"라고 요청해 10권의 목록을 받는다(1번). 그런 다음 책마다 다시 창구에 가서 "이 책 저자 정보 주세요"라고 10번 줄을 선다(N번).
- fetch join 방식: 처음부터 "추천 도서 목록을 **저자 정보와 함께** 주세요"라고 한 번에 요청한다.
- 배치 페치 방식: 목록을 받은 뒤 "이 10권의 저자 정보를 한꺼번에 주세요"라고 한 번 더 요청한다.

비유와 다른 점은, JPA에서는 "창구에 다시 가는 일"이 **개발자 모르게** 일어난다는 것이다. `team.getMembers()`처럼 평범한 getter 호출이 내부에서 SQL을 실행한다.

## 동작 원리

### 지연 로딩과 프록시

연관 관계를 `FetchType.LAZY`로 설정하면, 엔티티를 조회할 때 연관 엔티티는 바로 가져오지 않는다. 그 자리에는 **프록시 객체**(단일 연관)나 **아직 초기화되지 않은 컬렉션**(컬렉션 연관)이 들어간다. 이 객체의 데이터에 처음 접근하는 순간 Hibernate가 SQL을 실행해 채운다.

즉 LAZY는 쿼리를 **없애는 것이 아니라 미루는 것**이다. 엔티티 N개를 반복문으로 돌며 각자의 연관에 접근하면 쿼리가 N번 나간다.

### 즉시 로딩(EAGER)도 N+1을 만든다

"그럼 EAGER로 바꾸면 처음부터 같이 가져오지 않을까?"라고 생각하기 쉽지만, 그렇지 않을 수 있다.

JPQL(그리고 Spring Data JPA의 쿼리 메서드)은 **작성한 쿼리를 그대로** SQL로 바꾼다. `select t from Team t`는 팀 테이블만 조회한다. 결과를 받은 뒤에야 Hibernate는 "이 연관은 EAGER니까 지금 채워야 한다"는 것을 확인하고 **추가 쿼리**로 연관을 가져온다. Hibernate 사용자 가이드도 EAGER 연관을 JPQL에서 `JOIN FETCH`하지 않으면 보조 쿼리로 초기화되어 N+1이 생길 수 있다고 설명한다.

게다가 EAGER는 그 연관이 필요 없는 화면에서도 항상 로딩되므로 조정할 방법이 없다. 그래서 **연관은 기본적으로 LAZY로 두고, 필요한 쿼리에서만 함께 가져오는 것**이 일반적인 권장 방식이다.

| 연관 애너테이션 | JPA 기본 fetch 타입 |
| --- | --- |
| `@ManyToOne`, `@OneToOne` | `EAGER` |
| `@OneToMany`, `@ManyToMany` | `LAZY` |

`@ManyToOne`의 기본값이 EAGER라는 점을 놓치기 쉽다. `@ManyToOne(fetch = FetchType.LAZY)`처럼 명시하자.

### 해결책 1: fetch join

JPQL에 `join fetch`를 쓰면 연관 엔티티를 **같은 SQL의 JOIN으로** 함께 가져와 바로 채운다.

```sql
-- select t from Team t join fetch t.members
select t.*, m.* from team t join member m on m.team_id = t.id;
```

쿼리 한 번으로 끝나지만 주의할 점이 있다.

- 컬렉션을 fetch join하면 SQL 결과는 **회원 수만큼 행이 늘어난다**(팀 1개에 회원 5명이면 5행). JPA 스펙상 같은 팀이 결과에 여러 번 나올 수 있다. Hibernate 6부터는 이 중복을 자동으로 제거하므로 `distinct`를 쓸 필요가 없지만, 그 이전 버전에서는 `distinct`가 필요했다.
- 컬렉션 fetch join은 **페이징과 함께 쓰면 안 된다**(아래에서 설명).
- Hibernate에서 `List` 타입 컬렉션(bag) 두 개 이상을 동시에 fetch join하면 `MultipleBagFetchException`이 난다. 가능하더라도 컬렉션 여러 개를 한 번에 조인하면 행 수가 곱으로 불어나므로 피하는 것이 좋다.

### 해결책 2: `@EntityGraph`

JPA 엔티티 그래프는 "이번 조회에서 함께 가져올 속성"을 쿼리 문자열 밖에서 지정하는 방법이다. Spring Data JPA에서는 리포지토리 메서드에 `@EntityGraph(attributePaths = ...)`를 붙여 JPQL을 직접 쓰지 않고도 지정할 수 있다. Hibernate는 보통 이것을 조인으로 처리하므로 효과는 fetch join과 비슷하고, 컬렉션과 페이징에 관한 주의 사항도 똑같이 적용된다.

엔티티 그래프에는 두 가지 의미가 있다.

- **fetch graph**: 그래프에 지정한 속성은 EAGER로, 지정하지 않은 속성은 LAZY로 다룬다.
- **load graph**: 지정한 속성은 EAGER로, 지정하지 않은 속성은 매핑에 정의된 fetch 타입을 따른다.

Spring Data JPA의 `@EntityGraph`는 `type` 속성으로 둘 중 하나를 고를 수 있다.

### 해결책 3: 배치 페치

연관을 미리 함께 가져오지 않고, 지연 로딩이 일어날 때 **아직 초기화되지 않은 같은 종류의 프록시·컬렉션을 한꺼번에** 초기화하는 Hibernate 기능이다.

- 엔티티나 컬렉션에 `@BatchSize(size = 100)`를 붙이거나,
- `hibernate.default_batch_fetch_size`로 전역 기본값을 정한다. (이 설정이 없으면 Hibernate는 `@BatchSize`가 명시된 곳에만 배치 페치를 쓴다.)

첫 번째 팀의 회원에 접근하는 순간, Hibernate는 영속성 컨텍스트에 있는 다른 팀들의 미초기화 컬렉션까지 모아 한 번에 조회한다.

```sql
select m.* from member m where m.team_id in (1, 2, 3, ..., 10);
```

쿼리 수는 대략 **1 + ⌈N / 배치 크기⌉** 가 된다. 루트 쿼리는 그대로 두므로 **페이징과 함께 쓸 수 있다**는 것이 큰 장점이다. 실제 SQL 형태(IN 목록, 배열 파라미터 등)는 Hibernate 버전과 DB 방언에 따라 다르다.

### 해결책 4: DTO 프로젝션

화면에 필요한 값만 담은 DTO를 JPQL의 `select new ...`나 인터페이스 프로젝션으로 직접 조회하면, 엔티티 연관을 따라갈 일 자체가 없다. Hibernate 가이드도 배치 페치보다 DTO 프로젝션이나 fetch join이 대부분 더 나은 선택이라고 설명한다. 단, 조회한 결과는 엔티티가 아니므로 변경 감지로 수정할 수는 없다.

### 컬렉션 fetch join과 페이징

`join fetch t.members`에 `Pageable`이나 `setMaxResults`를 함께 쓰면 문제가 생긴다. SQL 결과가 회원 수만큼 늘어난 상태라, DB에서 `LIMIT 10`을 걸면 "팀 10개"가 아니라 "조인된 행 10개"가 잘린다. 그래서 Hibernate는 **DB에서 페이징하지 않고 모든 결과를 가져온 뒤 메모리에서 페이징**한다. 경고 로그만 남기고 동작하기 때문에, 데이터가 많아지면 메모리 부족과 심각한 성능 저하로 이어진다.

`hibernate.query.fail_on_pagination_over_collection_fetch=true`로 설정하면 이런 쿼리를 경고 대신 **예외**로 막을 수 있다. 해결 방법은 다음과 같다.

- 루트 엔티티만 페이징 조회하고, 컬렉션은 **배치 페치**로 채운다.
- 또는 1단계로 ID만 페이징 조회하고, 2단계로 `where t.id in :ids`에 컬렉션 fetch join을 쓴다.

`@ManyToOne`처럼 **단일 값 연관**의 fetch join은 행 수가 늘어나지 않으므로 페이징과 함께 써도 된다.

## 코드 예시

### 엔티티: 연관은 LAZY로

```java
@Entity
public class Team {
    @Id @GeneratedValue
    private Long id;

    private String name;

    @OneToMany(mappedBy = "team") // 기본값 LAZY
    private List<Member> members = new ArrayList<>();

    // getter 생략
}

@Entity
public class Member {
    @Id @GeneratedValue
    private Long id;

    private String name;

    @ManyToOne(fetch = FetchType.LAZY) // 기본값이 EAGER이므로 명시한다
    @JoinColumn(name = "team_id")
    private Team team;

    // getter 생략
}
```

### fetch join과 `@EntityGraph`

```java
public interface TeamRepository extends JpaRepository<Team, Long> {

    // JPQL fetch join
    @Query("select t from Team t join fetch t.members")
    List<Team> findAllWithMembers();

    // 같은 효과를 @EntityGraph로
    @EntityGraph(attributePaths = "members")
    List<Team> findByNameContaining(String keyword);
}

public interface MemberRepository extends JpaRepository<Member, Long> {

    // 단일 값 연관(@ManyToOne)은 페이징과 함께 써도 안전하다
    @EntityGraph(attributePaths = "team")
    Page<Member> findByNameStartingWith(String prefix, Pageable pageable);
}
```

### 배치 페치 설정 (Spring Boot)

```yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
        # 컬렉션 fetch join + 페이징을 예외로 막기
        query:
          fail_on_pagination_over_collection_fetch: true

logging:
  level:
    org.hibernate.SQL: debug # 실행되는 SQL 확인
```

특정 연관에만 적용하려면 애너테이션을 쓴다.

```java
@OneToMany(mappedBy = "team")
@BatchSize(size = 100) // org.hibernate.annotations.BatchSize
private List<Member> members = new ArrayList<>();
```

### 페이징 + 컬렉션: 루트만 페이징하고 배치 페치로 채우기

```java
@Transactional(readOnly = true)
public Page<TeamResponse> findTeams(Pageable pageable) {
    Page<Team> teams = teamRepository.findAll(pageable); // DB에서 LIMIT/OFFSET
    // members 접근 시 배치 페치로 IN 쿼리 한두 번에 초기화된다
    return teams.map(team -> new TeamResponse(team.getName(), team.getMembers().size()));
}
```

### DTO 프로젝션

```java
public record TeamMemberCount(String teamName, long memberCount) {}

@Query("""
        select new com.example.team.TeamMemberCount(t.name, count(m))
        from Team t left join t.members m
        group by t.id, t.name
        """)
List<TeamMemberCount> findMemberCounts();
```

## 언제 사용해야 할까?

| 방법 | 쿼리 수 | 페이징 | 적합한 상황 |
| --- | --- | --- | --- |
| fetch join | 1 | 단일 값 연관만 안전, 컬렉션은 불가 | 특정 화면에서 연관을 항상 함께 쓸 때 |
| `@EntityGraph` | 1 | fetch join과 동일 | 쿼리 메서드 이름을 유지하면서 연관만 함께 가져오고 싶을 때 |
| 배치 페치 | 1 + ⌈N/배치 크기⌉ | 가능 | 컬렉션 + 페이징, 여러 화면에서 공통으로 N+1을 완화하고 싶을 때 |
| DTO 프로젝션 | 1 | 가능 | 조회 전용 화면, 통계·집계, 필요한 컬럼이 일부뿐일 때 |
| EAGER로 변경 | 상황에 따라 다름 | — | **권장하지 않는다.** N+1을 해결하지 못하고 불필요한 로딩만 늘 수 있다 |

실무에서는 **모든 연관을 LAZY로 두고 `default_batch_fetch_size`를 전역으로 설정**해 기본적인 N+1을 완화한 뒤, 성능이 중요한 조회에만 fetch join이나 DTO 프로젝션을 적용하는 조합을 많이 쓴다.

## 주의 사항과 흔한 오해

- **"EAGER로 바꾸면 N+1이 해결된다"** — JPQL 조회 후 EAGER 연관을 추가 쿼리로 채우므로 N+1이 그대로 생길 수 있다. 오히려 필요 없는 곳에서도 항상 로딩된다.
- **"LAZY면 N+1이 안 생긴다"** — LAZY는 쿼리 시점을 미룰 뿐이다. 반복문 안에서 연관에 접근하면 그때 N번이 나간다.
- **"fetch join이면 항상 정답이다"** — 컬렉션 fetch join은 페이징과 함께 쓰면 메모리 페이징이 일어나고, 컬렉션 여러 개를 함께 조인하면 결과 행이 곱으로 늘어난다. 상황에 맞게 배치 페치나 쿼리 분리를 고르자.
- **fetch join 대상에 조건을 걸어 컬렉션 일부만 가져오지 말자.** JPA 스펙은 fetch join 대상에 별칭(식별 변수)을 허용하지 않는다. Hibernate는 허용하지만, 일부만 담긴 컬렉션이 영속성 컨텍스트에 올라가면 "전체 컬렉션"으로 오해되어 잘못된 데이터 처리로 이어질 수 있다.
- **JSON 직렬화가 N+1을 일으킬 수 있다.** 컨트롤러에서 엔티티를 그대로 반환하면 Jackson이 getter를 호출하며 지연 로딩을 연쇄적으로 일으킨다. Spring Boot는 기본으로 OSIV(Open EntityManager in View)를 켜 두어 이때도 지연 로딩이 동작하기 때문에, 문제가 조용히 숨는다. 응답은 DTO로 변환하고, 필요하면 `spring.jpa.open-in-view=false`를 검토하자.
- **트랜잭션과 영속성 컨텍스트가 끝난 뒤** 지연 로딩에 접근하면 `LazyInitializationException`이 난다. 이것을 피하려고 EAGER로 바꾸지 말고, 필요한 연관을 조회 시점에 함께 가져오자.
- **측정으로 확인하자.** `org.hibernate.SQL` 로그나 Hibernate 통계(`hibernate.generate_statistics`)로 요청당 실행되는 쿼리 수를 확인하는 습관이 가장 확실한 예방책이다.
