## 왜 필요한가?

네트워크 요청, 파일 읽기, 타이머처럼 **결과가 나중에 나오는 작업**은 JavaScript에서 흔하다. Promise가 없던 시절에는 이런 작업을 콜백 함수로 처리했다.

```javascript
getUser(id, (err, user) => {
  if (err) return handleError(err)
  getOrders(user.id, (err, orders) => {
    if (err) return handleError(err)
    getDetail(orders[0].id, (err, detail) => {
      if (err) return handleError(err)
      render(detail)
    })
  })
})
```

단계가 늘어날수록 들여쓰기가 깊어지고, 단계마다 에러 처리를 반복해야 한다. 콜백을 두 번 호출하거나 아예 호출하지 않는 실수도 막기 어렵다. 여러 작업을 동시에 시작하고 "모두 끝나면" 무언가를 하려면 직접 카운터를 관리해야 한다.

**Promise**는 "나중에 나올 결과"를 값처럼 주고받을 수 있는 객체로 만들어 이 문제를 정리한다. 그리고 **async/await**는 Promise를 기반으로 비동기 코드를 위에서 아래로 읽히는 모양으로 쓰게 해 준다.

## 쉽게 이해하는 비유

**카페의 진동벨**을 떠올려 보자.

- 주문하면 커피 대신 **진동벨(Promise)** 을 받는다. 아직 커피가 나오지 않은 상태가 **대기(pending)** 다.
- 커피가 나오면 벨이 울린다 → **이행(fulfilled)**. 재료가 떨어져 주문이 취소되면 → **거부(rejected)**.
- 한 번 울린 벨은 다시 "대기"로 돌아가지 않는다. 결과는 한 번만 정해진다.
- "벨이 울리면 커피를 받아 자리로 간다"고 미리 정해 두는 것이 `then`이다. 벨을 받은 뒤 다른 일을 하다가 나중에 `then`을 등록해도 결과를 받을 수 있다.
- `await`는 "벨이 울릴 때까지 **이 일은** 잠시 멈추고, 그동안 카운터는 다른 손님을 받는" 것이다. 카페 전체가 멈추는 것이 아니다.

비유와 다른 점은, 진동벨이 울려도 콜백이 **즉시** 실행되지는 않는다는 것이다. 콜백은 마이크로태스크로 예약되어 현재 실행 중인 코드가 끝난 뒤 실행된다.

## 동작 원리

### Promise의 세 가지 상태

| 상태 | 의미 |
| --- | --- |
| 대기 (pending) | 아직 결과가 정해지지 않았다 |
| 이행 (fulfilled) | 작업이 성공했고 결과 값이 있다 |
| 거부 (rejected) | 작업이 실패했고 실패 이유(보통 `Error`)가 있다 |

이행 또는 거부된 상태를 묶어 **확정(settled)** 이라고 한다. Promise는 한 번 확정되면 다시 바뀌지 않는다.

```javascript
const promise = new Promise((resolve, reject) => {
  // executor는 new Promise 호출 시 즉시(동기적으로) 실행된다
  setTimeout(() => resolve('완료'), 1000)
})
```

`resolve`에 **다른 Promise**를 넘기면 그 Promise의 결과를 따라가게 된다. 이때 바깥 Promise는 "resolve는 호출되었지만 아직 대기 중"일 수 있다. 그래서 MDN은 resolved(결정됨)와 fulfilled(이행됨)를 구분한다.

### then 체이닝

`then(onFulfilled, onRejected)`는 **항상 새 Promise를 반환**한다. 새 Promise의 결과는 콜백이 무엇을 하느냐에 따라 정해진다.

- 값을 반환하면 → 그 값으로 이행된다.
- Promise를 반환하면 → 그 Promise의 결과를 따른다(체인이 그것을 기다린다).
- 예외를 던지면 → 그 예외로 거부된다.

그래서 단계를 평평하게 이어 붙일 수 있다.

```javascript
getUser(id)
  .then((user) => getOrders(user.id)) // Promise를 반환 → 다음 then이 기다린다
  .then((orders) => getDetail(orders[0].id))
  .then(render)
  .catch(handleError) // 위의 어느 단계에서 실패해도 여기로 온다
  .finally(hideSpinner) // 성공·실패와 상관없이 실행된다
```

`catch(fn)`은 `then(undefined, fn)`과 같다. 거부는 처리할 콜백을 만날 때까지 체인을 따라 내려가므로, 동기 코드의 `try...catch`처럼 **한 곳에서** 에러를 처리할 수 있다. `catch`에서 값을 반환하면 체인은 다시 이행 상태로 이어진다.

### 여러 Promise 조합하기

| 메서드 | 이행 조건 | 거부 조건 | 용도 |
| --- | --- | --- | --- |
| `Promise.all` | 모두 이행 → 결과 배열 | 하나라도 거부되면 즉시 거부 | 모두 필요할 때 |
| `Promise.allSettled` | 모두 확정되면 항상 이행 → 각 결과의 상태 객체 배열 | 거부되지 않는다 | 일부 실패해도 결과를 모두 볼 때 |
| `Promise.race` | 가장 먼저 **확정**된 것이 이행이면 이행 | 가장 먼저 확정된 것이 거부면 거부 | 타임아웃 구현 |
| `Promise.any` | 가장 먼저 **이행**된 것으로 이행 | 모두 거부되면 `AggregateError`로 거부 | 여러 대체 경로 중 하나만 성공하면 될 때 |

`Promise.all`이 거부되어도 **나머지 작업이 취소되지는 않는다.** Promise에는 취소 기능이 없으므로, 실제 작업을 멈추려면 `fetch`의 `AbortController` 같은 별도 수단이 필요하다.

### async 함수와 await

`async` 함수는 **항상 Promise를 반환**한다.

- 함수가 값을 `return`하면 반환된 Promise가 그 값으로 이행된다.
- 함수 안에서 예외가 발생하면 반환된 Promise가 그 예외로 거부된다.

`await expr`는 다음과 같이 동작한다.

1. `expr`이 Promise가 아니면 이미 이행된 Promise로 감싼다.
2. **async 함수의 실행을 일시 중단**하고, 호출한 쪽으로 제어를 돌려준다. 콜 스택이 막히지 않으므로 다른 코드가 계속 실행된다.
3. Promise가 이행되면 함수가 **마이크로태스크로 재개**되고 `await` 식은 이행 값이 된다. 거부되면 그 자리에서 예외가 던져진 것처럼 동작하므로 `try...catch`로 잡을 수 있다.

```javascript

  console.log('1')

console.log('2')

```

이미 결과가 있는 값을 `await`해도 나머지 코드는 **현재 동기 코드가 끝난 뒤** 실행된다. `await` 뒤의 코드는 사실상 `then` 콜백과 같은 시점에 실행된다고 생각하면 된다.

## 코드 예시

### async/await와 에러 처리

```typescript
async function loadUserName(id: string): Promise<string> {
  const res = await fetch(`/api/users/${id}`)
  // fetch는 HTTP 404·500에서도 거부되지 않는다. 직접 확인해야 한다
  if (!res.ok) throw new Error(`HTTP ${res.status}`)
  const user: { name: string } = await res.json()
  return user.name // 반환된 Promise가 이 값으로 이행된다
}

async function main() {
  try {
    const name = await loadUserName('42')
    console.log(name)
  } catch (err) {
    // 네트워크 오류, HTTP 오류, JSON 파싱 오류가 모두 여기로 온다
    console.error('불러오기 실패', err)
  } finally {
    console.log('정리 작업')
  }
}
```

### 순차 실행과 병렬 실행

서로 독립적인 두 요청이 각각 1초 걸린다고 하자.

```javascript
// [느림] 순차 실행: 약 2초. 첫 요청이 끝나야 두 번째 요청을 시작한다
async function sequential() {
  const user = await fetchUser()
  const posts = await fetchPosts()
  return { user, posts }
}

// [빠름] 병렬 실행: 약 1초. 두 요청을 먼저 모두 시작하고 함께 기다린다
async function parallel() {
  const [user, posts] = await Promise.all([fetchUser(), fetchPosts()])
  return { user, posts }
}
```

두 번째 요청이 첫 번째 결과에 **의존한다면** 순차 실행이 맞다. 의존하지 않는데 습관적으로 `await`를 이어 쓰면 불필요하게 느려진다.

반복문에서도 같은 함정이 있다.

```javascript
// 순차: 하나씩 기다린다 (순서가 중요하거나 요청 수를 제한해야 할 때)
for (const id of ids) {
  results.push(await fetchItem(id))
}

// 병렬: 모두 시작하고 함께 기다린다
const all = await Promise.all(ids.map((id) => fetchItem(id)))

// 주의: forEach는 콜백이 반환한 Promise를 기다리지 않는다
ids.forEach(async (id) => {
  await fetchItem(id) // forEach는 이걸 기다리지 않고 바로 끝난다
})
```

### 일부 실패를 허용하기

```javascript
const results = await Promise.allSettled([fetchA(), fetchB(), fetchC()])

for (const r of results) {
  if (r.status === 'fulfilled') console.log('성공', r.value)
  else console.warn('실패', r.reason)
}
```

### 타임아웃

```javascript
function timeout(ms) {
  return new Promise((_, reject) => setTimeout(() => reject(new Error('timeout')), ms))
}

// 먼저 확정되는 쪽을 따른다. 단, 느린 요청 자체가 취소되지는 않는다
const data = await Promise.race([fetchData(), timeout(3000)])
```

`fetch`라면 `AbortSignal.timeout(3000)`을 `signal` 옵션으로 넘기는 편이 요청까지 실제로 중단시킨다.

## 언제 사용해야 할까?

| 상황 | 선택 |
| --- | --- |
| 대부분의 애플리케이션 코드 | `async`/`await` + `try...catch` |
| 콜백 기반 API를 Promise로 바꾸기 | `new Promise((resolve, reject) => ...)` |
| 독립적인 작업 여러 개, 모두 필요 | `Promise.all` |
| 독립적인 작업 여러 개, 일부 실패 허용 | `Promise.allSettled` |
| 여러 대체 경로 중 하나만 성공하면 됨 | `Promise.any` |
| 가장 먼저 끝난 결과(성공·실패 무관)만 필요 | `Promise.race` |
| 간단한 변환 한두 단계 | `then` 체이닝도 충분하다 |

`async`/`await`와 `then`은 같은 Promise 위에서 동작하므로 섞어 써도 된다. 다만 한 함수 안에서는 한 가지 스타일로 통일하는 편이 읽기 쉽다.

## 주의 사항과 흔한 오해

- **"await는 스레드를 멈추고 기다린다"** — 멈추는 것은 **그 async 함수 하나**다. 함수는 Promise를 반환하고 빠져나가며, 그동안 이벤트 루프는 다른 작업을 계속 처리한다.
- **"async 함수는 결과 값을 바로 반환한다"** — 항상 Promise를 반환한다. 호출하는 쪽도 `await`하거나 `then`으로 결과를 받아야 한다.
- **"Promise를 만들면 그때부터 비동기로 실행된다"** — `new Promise`의 executor는 **즉시 동기적으로** 실행된다. 비동기인 것은 `then` 콜백과 `await` 이후의 재개다. 또 executor 안에서 무거운 계산을 하면 그대로 메인 스레드를 막는다.
- **처리되지 않은 거부(unhandled rejection)**: 거부된 Promise에 `catch`가 없으면 에러가 조용히 사라지지 않는다. 브라우저는 `unhandledrejection` 이벤트를 발생시키고 콘솔에 에러를 출력한다. Node.js는 15 버전부터 기본 모드가 `throw`로 바뀌어, `unhandledRejection` 리스너가 없으면 잡히지 않은 예외로 처리되어 프로세스가 종료된다. 체인 끝에는 반드시 `catch`를 두거나 `await`를 `try...catch`로 감싸자.
- **`await` 없이 async 함수를 호출하고 잊어버리기** — 반환된 Promise가 거부되어도 아무도 처리하지 않는다. 의도적으로 기다리지 않는다면 `.catch`라도 붙인다.
- **`return await`와 `return`의 차이** — `try` 블록 안에서 `return promise`를 하면 그 Promise의 거부는 이 함수의 `catch`에서 잡히지 않는다. `try` 안에서 잡고 싶다면 `return await promise`를 쓴다.
- **"Promise.all이 실패하면 나머지 요청도 취소된다"** — 결과를 기다리지 않을 뿐, 이미 시작된 작업은 계속 진행된다.
- **"fetch는 HTTP 에러에서 거부된다"** — `fetch`는 네트워크 오류일 때만 거부된다. 404·500 응답은 이행되므로 `res.ok`를 확인해야 한다.
