## 왜 필요한가?

React 컴포넌트의 렌더링은 **순수한 계산**이어야 한다. props와 state를 받아 JSX를 반환할 뿐, 렌더링 중에 서버에 연결하거나 DOM을 직접 건드리면 안 된다. 렌더링은 여러 번 일어날 수 있고, 개발 환경에서는 일부러 두 번 호출되기도 하기 때문이다.

하지만 실제 앱은 React 바깥의 세계와 연결되어야 한다.

- 채팅방 컴포넌트가 화면에 있는 동안 **채팅 서버에 연결**되어 있어야 한다.
- 지도·차트 같은 **React가 아닌 위젯**을 props에 맞게 설정해야 한다.
- 브라우저의 `resize` 이벤트를 구독하거나 `document.title`을 바꿔야 한다.

이런 작업은 특정 클릭 같은 이벤트 때문이 아니라 **"이 컴포넌트가 화면에 이런 상태로 있다"는 사실 때문에** 필요하다. 이벤트 핸들러에 넣을 수도, 렌더링 중에 실행할 수도 없는 이 작업을 위한 자리가 **Effect**이고, 그것을 선언하는 Hook이 `useEffect`다.

## 쉽게 이해하는 비유

**에어컨의 희망 온도**를 떠올려 보자.

- 사용자는 "희망 온도 24도"라는 **상태**만 정한다. 이것이 렌더링 결과다.
- 에어컨(Effect)은 실제 방 온도(외부 시스템)를 그 설정에 **맞춰 놓는다**.
- 희망 온도가 26도로 바뀌면, 에어컨은 기존 설정을 정리하고(클린업) 새 설정으로 다시 맞춘다(setup).
- 희망 온도가 그대로면 아무것도 하지 않는다. 이것이 **의존성 배열**의 역할이다.
- 에어컨을 끄고 방을 나가면(언마운트) 마지막 정리를 한다.

중요한 것은 Effect를 "마운트될 때 한 번 실행되는 코드"가 아니라 **"현재 상태에 맞춰 외부 시스템을 동기화하는 코드"** 로 생각하는 것이다. 비유와 달리 에어컨은 온도를 계속 감시하지만, Effect는 의존성이 바뀐 커밋 뒤에만 다시 실행된다.

## 동작 원리

### 기본 형태

```tsx
useEffect(() => {
  // setup: 외부 시스템과 연결·동기화
  const connection = createConnection(serverUrl, roomId)
  connection.connect()

  return () => {
    // cleanup: setup이 한 일을 되돌린다
    connection.disconnect()
  }
}, [serverUrl, roomId]) // 의존성: setup이 사용하는 반응형 값 전부
```

### 실행 시점

1. 컴포넌트가 렌더링되고 결과가 DOM에 **커밋된 뒤** Effect가 실행된다. 렌더링 중에는 실행되지 않는다.
2. 상호작용(클릭 등)으로 인한 경우가 아니라면 React는 일반적으로 **브라우저가 화면을 그리게 한 뒤** Effect를 실행한다.
3. 클릭 같은 상호작용으로 인한 경우에는 화면을 그리기 **전에** Effect를 실행할 수도 있다. react.dev는 이벤트 시스템이 Effect의 결과를 관찰할 수 있게 하기 위해서라고 설명한다.

Effect가 툴팁 위치 계산처럼 **화면에 보이는 것을 바꾸는데** 그리기 전후의 깜빡임이 눈에 띈다면 `useLayoutEffect`를 쓴다. `useLayoutEffect`는 브라우저가 그리기 전에 실행되어 화면 갱신을 막는다.

### 의존성 배열

| 형태 | 언제 다시 실행되나 |
| --- | --- |
| `useEffect(fn, [a, b])` | 첫 커밋 후, 그리고 `a`나 `b`가 바뀐 커밋 후 |
| `useEffect(fn, [])` | 첫 커밋 후에만 (개발 환경 Strict Mode에서는 한 번 더) |
| `useEffect(fn)` | **모든** 커밋 후 |

- React는 각 의존성을 이전 값과 `Object.is`로 비교한다. 렌더링마다 새로 만드는 객체나 함수를 의존성에 넣으면 매번 "바뀌었다"고 판단한다.
- 의존성은 **고르는 것이 아니다.** Effect 안에서 읽는 props, state, 그리고 컴포넌트 안에서 선언된 값(반응형 값)은 모두 넣어야 한다. React용 린터 규칙(`react-hooks/exhaustive-deps`)이 빠진 의존성을 알려 준다.
- 어떤 값을 의존성에서 빼고 싶다면 배열에서 지우는 것이 아니라, **Effect가 그 값을 쓰지 않도록 코드를 바꿔야** 한다.

### 클린업

의존성이 바뀌면 React는 다음 순서로 동작한다.

1. **이전 렌더의 값**으로 클린업을 실행한다(예: 이전 방과의 연결 해제).
2. **새 렌더의 값**으로 setup을 실행한다(예: 새 방에 연결).

컴포넌트가 화면에서 제거되면 클린업이 마지막으로 한 번 실행된다. 클린업은 setup이 한 일을 **대칭적으로 되돌려야** 한다. 구독했다면 구독 해제, 타이머를 걸었다면 해제, 연결했다면 연결 해제다.

### 개발 환경의 Strict Mode: setup → cleanup → setup

Strict Mode가 켜진 개발 환경에서 React는 컴포넌트가 처음 마운트될 때 **실제 setup 전에 setup과 cleanup을 한 번 더 실행**한다.

"Effect가 두 번 실행된다"고 놀라서 Strict Mode를 끄거나 `useRef`로 막는 것은 해결책이 아니다. 클린업을 제대로 구현하면 setup → cleanup → setup은 setup 한 번과 **사용자 입장에서 구별되지 않는다.** 이 동작은 프로덕션에서는 일어나지 않는다.

## 코드 예시

### 외부 시스템 구독

```tsx
import { useEffect, useState } from 'react'

function useWindowWidth() {
  const [width, setWidth] = useState(() => window.innerWidth)

  useEffect(() => {
    function handleResize() {
      setWidth(window.innerWidth)
    }
    window.addEventListener('resize', handleResize)
    return () => window.removeEventListener('resize', handleResize) // 구독과 대칭
  }, []) // 반응형 값을 읽지 않으므로 빈 배열

  return width
}
```

브라우저 API나 외부 저장소를 구독하는 경우에는 이런 목적을 위해 만들어진 `useSyncExternalStore`도 선택지다.

### 데이터 가져오기와 경쟁 상태(race condition)

사용자가 `Alice`를 고른 뒤 바로 `Bob`을 골랐는데, `Alice` 응답이 더 늦게 도착하면 화면에 `Bob`을 선택한 채로 `Alice`의 정보가 보인다. 네트워크 응답은 보낸 순서대로 도착한다는 보장이 없기 때문이다. 클린업에서 이전 요청의 결과를 무시하도록 표시하면 이를 막을 수 있다.

```tsx
import { useEffect, useState } from 'react'

type Bio = { name: string; text: string }

function Profile({ person }: { person: string }) {
  const [bio, setBio] = useState<Bio | null>(null)

  useEffect(() => {
    let ignore = false // 이 Effect 실행 한 번에만 속한 플래그
    setBio(null)

    fetch(`/api/bio/${encodeURIComponent(person)}`)
      .then((res) => res.json())
      .then((result: Bio) => {
        if (!ignore) setBio(result) // 이미 다른 person으로 바뀌었다면 무시
      })

    return () => {
      ignore = true // person이 바뀌거나 언마운트되면 이전 요청 결과를 버린다
    }
  }, [person])

  return <p>{bio ? bio.text : '불러오는 중...'}</p>
}
```

요청 자체를 중단하고 싶다면 `AbortController`를 만들어 `fetch`의 `signal`로 넘기고, 클린업에서 `controller.abort()`를 호출한다. 이때 중단된 요청의 `AbortError`는 따로 처리해야 한다.

Effect 함수 자체를 `async`로 만들면 안 된다. `async` 함수는 Promise를 반환하는데, Effect는 클린업 함수나 아무것도 반환하지 않아야 하기 때문이다. 위처럼 `then`을 쓰거나 Effect 안에 `async` 함수를 선언하고 호출한다.

<Callout type="tip" title="실제 프로젝트의 데이터 가져오기">
react.dev는 Effect로 직접 데이터를 가져오는 방식이 서버 렌더링, 네트워크 폭포(waterfall), 캐싱 측면에서 불리하다고 설명한다. 프레임워크를 쓴다면 프레임워크의 데이터 로딩 기능을, 아니라면 클라이언트 측 캐시 라이브러리를 고려하자. 위 예시는 Effect의 동작 원리를 이해하기 위한 것이다.
</Callout>

### Effect가 필요 없는 경우

**props·state로 계산할 수 있는 값**은 state와 Effect로 동기화하지 말고 렌더링 중에 계산한다.

```tsx
// [나쁨] 불필요한 state와 Effect: 렌더링이 한 번 더 일어나고 한 박자 늦은 값이 보인다
const [fullName, setFullName] = useState('')
useEffect(() => {
  setFullName(firstName + ' ' + lastName)
}, [firstName, lastName])

// [좋음] 렌더링 중에 계산한다
const fullName = firstName + ' ' + lastName
```

계산이 비싸다면 `useMemo`로 캐시한다.

**특정 사용자 행동에 대한 처리**는 이벤트 핸들러에 둔다.

```tsx
// [나쁨] "구매 버튼을 눌렀다"는 사실이 아니라 state 변화에 반응한다
useEffect(() => {
  if (product.isInCart) showNotification(`${product.name}을(를) 장바구니에 담았다`)
}, [product])

// [좋음] 어떤 행동 때문에 일어나는 일인지가 분명하다
function handleBuyClick() {
  addToCart(product)
  showNotification(`${product.name}을(를) 장바구니에 담았다`)
}
```

첫 번째 코드는 페이지를 새로고침해 장바구니에 이미 담긴 상품이 다시 표시될 때도 알림을 띄운다. 판단 기준은 **"이 코드가 왜 실행되어야 하는가?"** 다. 사용자가 무언가를 했기 때문이라면 이벤트 핸들러, 컴포넌트가 화면에 표시되었기 때문이라면 Effect다.

## 언제 사용해야 할까?

| 하고 싶은 일 | 어디에 둘까 |
| --- | --- |
| 서버 연결, 구독, 브라우저 API·서드파티 위젯 동기화 | `useEffect` + 클린업 |
| 화면에 표시되었다는 이유로 필요한 데이터 요청 | `useEffect` + 경쟁 상태 처리 (또는 프레임워크·라이브러리) |
| props·state로 계산되는 값 | 렌더링 중 계산 (비싸면 `useMemo`) |
| 버튼 클릭, 폼 제출 등에 따른 요청·알림 | 이벤트 핸들러 |
| prop이 바뀌면 state 전체 초기화 | 컴포넌트에 `key`를 다르게 주기 |
| 그리기 전에 레이아웃을 측정하고 반영 | `useLayoutEffect` |

## 주의 사항과 흔한 오해

- **"useEffect는 componentDidMount의 Hook 버전이다"** — 생명주기가 아니라 **동기화**로 생각해야 한다. Effect는 의존성이 바뀔 때마다 이전 동기화를 정리하고 다시 동기화한다.
- **"빈 배열 `[]`이면 무조건 한 번만 실행된다"** — 개발 환경 Strict Mode에서는 setup → cleanup → setup으로 한 번 더 실행된다. 그리고 반응형 값을 사용하면서 `[]`를 쓰면 오래된 값을 보는 버그가 생긴다.
- **"의존성을 빼서 무한 루프를 막는다"** — 린터 경고를 무시하고 의존성을 빼면 Effect가 오래된 props·state를 보게 된다. 대신 업데이터 함수(`setCount(c => c + 1)`)를 쓰거나, 객체·함수를 Effect 안으로 옮기는 등 의존성 자체를 줄인다.
- **Effect에서 state를 바꿔 무한 루프** — 의존성 배열이 없거나, Effect가 바꾸는 state가 자기 의존성에 들어 있으면 렌더 → Effect → state 변경 → 렌더가 반복된다.
- **"Effect는 항상 화면이 그려진 뒤 실행된다"** — 일반적으로는 그렇지만, 클릭 같은 상호작용으로 인한 경우 페인트 전에 실행될 수 있다. 페인트 전 실행이 반드시 필요하다면 `useLayoutEffect`를 쓴다.
- **클린업 없는 구독·타이머** — 언마운트 후에도 이벤트 리스너나 `setInterval`이 남아 메모리 누수와 중복 실행을 일으킨다. Strict Mode의 이중 실행은 바로 이런 누락을 개발 중에 드러내기 위한 장치다.
- **Effect는 서버 렌더링 중에 실행되지 않는다.** 클라이언트에서만 실행되므로 서버에서 만든 HTML에는 Effect의 결과가 반영되지 않는다.
