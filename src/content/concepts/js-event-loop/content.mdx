## 왜 필요한가?

브라우저의 JavaScript는 **한 스레드**에서 실행된다. 한 번에 한 줄씩, 하나의 콜 스택 위에서만 코드가 돈다. 그런데 웹 페이지는 동시에 여러 일을 해야 한다.

- 서버에 요청을 보내 놓고 응답을 기다리는 동안에도 버튼 클릭에 반응해야 한다.
- 3초 뒤에 알림을 띄우는 타이머를 걸어 두고, 그사이 다른 코드를 계속 실행해야 한다.

만약 JavaScript가 응답이 올 때까지, 타이머가 끝날 때까지 **멈춰서 기다린다면** 그동안 페이지는 완전히 굳는다. 그래서 JavaScript는 "기다리는 일"을 호스트 환경(브라우저나 Node.js)에 맡기고, 일이 끝나면 실행할 **콜백을 큐에 넣어 두었다가** 콜 스택이 비었을 때 하나씩 꺼내 실행한다. 이 "큐에서 꺼내 실행하기"를 끝없이 반복하는 장치가 **이벤트 루프**다.

이벤트 루프를 모르면 다음 코드의 출력 순서를 설명할 수 없다.

```javascript
console.log('A')
setTimeout(() => console.log('B'), 0)
Promise.resolve().then(() => console.log('C'))
console.log('D')
// 출력: A, D, C, B
```

지연 시간이 0인 `setTimeout`보다 `then` 콜백이 먼저 실행된다. 이 차이가 바로 **태스크와 마이크로태스크**의 차이다.

## 쉽게 이해하는 비유

**혼자 일하는 식당 주방장**을 떠올려 보자.

- 주방장(JavaScript 스레드)은 한 번에 한 요리만 만든다. 지금 만드는 요리가 **콜 스택**이다.
- 오븐 타이머나 배달 주문 확인은 주방장이 직접 지켜보지 않는다. 오븐과 주문 단말기(**호스트 환경의 Web API**)가 알아서 기다리다가, 끝나면 주문표를 **대기 줄(태스크 큐)** 에 꽂아 둔다.
- 주방장은 요리 하나를 끝낼 때마다, 다음 주문표를 받기 전에 **"방금 요리의 마무리 작업" 메모(마이크로태스크 큐)** 를 전부 처리한다. 마무리 도중에 새 마무리 메모가 생기면 그것까지 끝낸다.
- 마무리 메모가 하나도 남지 않으면 그제야 대기 줄에서 **주문표 한 장**을 가져온다.

비유가 틀리는 지점도 있다. 실제 브라우저에는 태스크 큐가 여러 개 있을 수 있고, 어느 큐에서 꺼낼지는 브라우저가 정한다. 또 주방장은 중간에 "가게 화면 갱신(렌더링)"도 해야 하는데, 이 비유와 아래 시뮬레이터에는 그 부분이 빠져 있다.

## 동작 원리

### 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| 콜 스택 (Call Stack) | 지금 실행 중인 함수들의 실행 컨텍스트. JavaScript 엔진이 관리한다. |
| 호스트 환경 API | 타이머, 네트워크, DOM 이벤트처럼 "기다리는 일"을 맡는 브라우저 기능. 흔히 Web API라고 부른다. |
| 태스크 큐 (Task Queue) | 타이머 만료, 이벤트 발생 등으로 실행 준비가 된 **태스크**가 모이는 곳 |
| 마이크로태스크 큐 (Microtask Queue) | Promise 반응(`then`/`catch`/`finally` 콜백), `queueMicrotask`, `MutationObserver` 콜백 등이 들어가는 곳 |

`setTimeout`이나 `fetch`, `addEventListener`는 JavaScript 언어(ECMAScript) 자체의 기능이 아니라 **호스트 환경이 제공하는 API**다. 이벤트 루프도 언어 명세가 아니라 HTML 표준(브라우저)과 Node.js가 각각 정의한다.

### 브라우저 이벤트 루프의 한 바퀴

HTML 표준의 처리 모델을 학습용으로 줄이면 다음과 같다.

1. 실행할 준비가 된 태스크가 있는 **태스크 큐 하나를 고르고**, 그 큐에서 **가장 오래된 태스크 하나**를 꺼내 실행한다. 스크립트 파일 전체를 실행하는 것도 하나의 태스크다.
2. 태스크가 끝나 콜 스택이 비면 **마이크로태스크 체크포인트(microtask checkpoint)** 를 수행한다. 마이크로태스크 큐가 빌 때까지 하나씩 꺼내 실행하며, 실행 도중 새로 추가된 마이크로태스크도 **같은 체크포인트 안에서** 처리한다.
3. 렌더링할 기회가 되면 화면을 갱신한다(스타일 계산, 레이아웃, `requestAnimationFrame` 콜백 등).
4. 1로 돌아간다.

핵심은 **태스크는 한 바퀴에 하나, 마이크로태스크는 큐가 빌 때까지 전부**라는 점이다.

<Callout type="info" title="표준 용어: 태스크와 마이크로태스크">
HTML 표준이 쓰는 용어는 **task**와 **microtask**다. 흔히 보이는 "매크로태스크(macrotask)"는 태스크를 마이크로태스크와 구분하려고 쓰는 비공식 표현이며 표준에는 없다. 또 표준에서 태스크 큐는 엄밀히 말해 "큐"가 아니라 **집합(set)** 이다. 브라우저는 실행 가능한 태스크 중 가장 오래된 것을 꺼내지만, **여러 태스크 큐 중 어느 것을 먼저 고를지**는 구현에 맡긴다. 예를 들어 사용자 입력 태스크를 타이머 태스크보다 우선 처리할 수 있다.
</Callout>

### 마이크로태스크는 태스크 사이에만 실행되는 것이 아니다

표준은 스크립트나 콜백 실행이 끝나 **JavaScript 실행 컨텍스트 스택이 비면** 마이크로태스크 체크포인트를 수행하도록 정한다. 그래서 하나의 클릭 이벤트에 리스너가 두 개 있으면, 사용자가 실제로 클릭했을 때는 첫 번째 리스너가 끝난 직후 그 리스너가 예약한 마이크로태스크가 먼저 실행되고 나서 두 번째 리스너가 실행된다. 반면 `element.click()`처럼 JavaScript 코드에서 이벤트를 발생시키면 그 호출이 끝날 때까지 스택이 비지 않으므로 순서가 달라진다.

### setTimeout은 어떻게 태스크 큐로 가는가

`setTimeout(cb, 100)`을 호출하면 다음이 일어난다.

1. 호스트 환경이 타이머를 등록하고 `setTimeout` 호출은 **즉시 반환**된다. 콜 스택은 다음 줄로 넘어간다.
2. 최소 100ms가 지나면 타이머가 만료되고, `cb`를 실행하는 **태스크**가 태스크 큐에 들어간다.
3. 이벤트 루프가 그 태스크를 꺼낼 차례가 되어야 `cb`가 실행된다.

그래서 지연 시간은 **"최소 이만큼 뒤"** 이지 "정확히 이때"가 아니다. 앞선 태스크가 오래 걸리거나 마이크로태스크가 계속 쌓이면 더 늦어진다. MDN에 따르면 이 밖에도 중첩된 `setTimeout`이 5단계 이상 이어지면 최소 4ms가 강제되고, 비활성 탭에서는 브라우저가 타이머를 더 크게 지연시킬 수 있다.

### Promise.then은 언제 마이크로태스크가 되는가

`then` 콜백은 **Promise가 이행(fulfilled)되거나 거부(rejected)된 뒤에** 마이크로태스크로 예약된다.

- `Promise.resolve().then(cb)`처럼 이미 이행된 Promise에 `then`을 붙이면 `cb`는 **즉시** 마이크로태스크 큐에 들어간다. 다만 실행은 현재 코드가 끝나고 콜 스택이 빈 뒤다.
- 아직 대기(pending) 중인 Promise에 `then`을 붙이면, 나중에 그 Promise가 이행되는 시점에 마이크로태스크가 예약된다.

`then` 콜백은 결코 동기적으로 실행되지 않는다. 그래서 "이미 결과가 있는 Promise"라도 `then` 콜백은 항상 현재 동기 코드보다 뒤에 실행된다.

### Node.js는 규칙이 다르다

Node.js도 이벤트 루프를 쓰지만 HTML 표준이 아니라 libuv 기반의 **단계(phase)** 로 구성된다. 공식 문서는 timers(`setTimeout`/`setInterval`), pending callbacks, poll(I/O), check(`setImmediate`), close callbacks 같은 단계를 설명한다.

- `process.nextTick` 콜백은 이벤트 루프 단계와 별개인 **next tick 큐**에 들어가며, 현재 작업이 끝나면 단계와 상관없이 처리된다. Node.js 문서에 따르면 next tick 큐를 비운 직후 Promise 마이크로태스크 큐를 비우므로, CommonJS 모듈에서는 `process.nextTick` 콜백이 `queueMicrotask`·`then` 콜백보다 먼저 실행된다. ES 모듈에서는 모듈 실행 자체가 마이크로태스크 처리 중에 일어나므로 순서가 반대가 된다.
- 메인 모듈에서 `setTimeout(cb, 0)`과 `setImmediate(cb)`의 실행 순서는 **정해져 있지 않다**. I/O 콜백 안에서 호출했다면 `setImmediate`가 항상 먼저다.

"Promise 콜백이 타이머보다 먼저"라는 큰 원칙은 같지만, 세부 순서를 브라우저 규칙으로 Node.js 코드를 예측하면 틀릴 수 있다.

## 코드 예시

### 마이크로태스크 안에서 예약한 마이크로태스크

```javascript
console.log('1: 동기')

setTimeout(() => console.log('2: 타이머 A'), 0)

Promise.resolve().then(() => {
  console.log('3: then 1')
  // 마이크로태스크 처리 중에 추가된 마이크로태스크도 같은 체크포인트에서 실행된다
  Promise.resolve().then(() => console.log('4: then 1 안의 then'))
})

setTimeout(() => console.log('5: 타이머 B'), 0)

console.log('6: 동기')

// 출력 순서
// 1: 동기
// 6: 동기
// 3: then 1
// 4: then 1 안의 then
// 2: 타이머 A
// 5: 타이머 B
```

1. 스크립트 태스크가 `1`, `6`을 출력하는 동안 타이머 두 개가 등록되고 `then 1`이 마이크로태스크 큐에 들어간다.
2. 스크립트가 끝나 콜 스택이 비면 마이크로태스크 체크포인트가 `3`을 출력하고, 그사이 추가된 마이크로태스크까지 실행해 `4`를 출력한다.
3. 그다음 태스크 큐에서 타이머 A, 타이머 B 태스크가 한 바퀴에 하나씩 실행된다.

### 타이머 안에서 예약한 Promise

```javascript
setTimeout(() => {
  console.log('타이머 1')
  Promise.resolve().then(() => console.log('타이머 1의 then'))
}, 0)

setTimeout(() => console.log('타이머 2'), 0)

// 출력 순서
// 타이머 1
// 타이머 1의 then   ← 타이머 1 태스크가 끝나자마자 마이크로태스크 체크포인트
// 타이머 2
```

두 타이머가 거의 동시에 만료되어도 "타이머 1 → 타이머 2 → then"이 아니다. 태스크 하나가 끝날 때마다 마이크로태스크가 먼저 비워지기 때문이다.

### 긴 작업이 타이머를 늦추는 예

```javascript
const start = Date.now()

setTimeout(() => {
  console.log(`실제 지연: ${Date.now() - start}ms`) // 100ms가 아니라 약 500ms 이상
}, 100)

// 콜 스택을 500ms 동안 점유한다
while (Date.now() - start < 500) {}
```

타이머는 100ms에 만료되어 태스크 큐에 들어가지만, 현재 스크립트 태스크가 끝나기 전에는 실행될 수 없다.

## 언제 사용해야 할까?

| 하고 싶은 일 | 선택 | 이유 |
| --- | --- | --- |
| 현재 코드가 끝난 직후, 다른 태스크나 렌더링보다 먼저 처리 | `queueMicrotask`, `Promise.then` | 같은 체크포인트 안에서 바로 실행된다 |
| 브라우저에 숨 돌릴 틈(입력 처리, 렌더링)을 준 뒤 이어서 처리 | `setTimeout(cb, 0)` 등 태스크 | 다음 태스크로 넘어가기 전에 다른 일이 끼어들 수 있다 |
| 다음 화면 그리기 직전에 애니메이션 갱신 | `requestAnimationFrame` | 렌더링 단계에 맞춰 호출된다 |
| CPU를 오래 쓰는 계산 | 작업 쪼개기, Web Worker | 메인 스레드를 막지 않는다 |

- 오래 걸리는 동기 작업은 이벤트 루프 전체를 멈춘다. 클릭도, 화면 갱신도, 타이머도 그동안 처리되지 않는다.
- 큰 작업을 잘게 나눌 때 마이크로태스크로 나누면 **렌더링 기회가 생기지 않는다**. 사용자 입력과 렌더링이 끼어들게 하려면 태스크 단위로 나눠야 한다.

## 주의 사항과 흔한 오해

- **"setTimeout(cb, 0)은 바로 실행된다"** — 아니다. 최소한 현재 실행 중인 코드와 대기 중인 마이크로태스크가 모두 끝난 뒤, 이벤트 루프가 그 태스크를 꺼낼 차례가 되어야 실행된다.
- **"setTimeout의 지연 시간은 정확하다"** — 지연 시간은 최소값이다. 앞선 작업, 중첩 타이머의 최소 지연, 비활성 탭 제한 등으로 늦어질 수 있다.
- **"매크로태스크 큐가 하나 있다"** — HTML 표준에는 "매크로태스크"라는 용어가 없고, 태스크 큐는 여러 개일 수 있다. 서로 다른 태스크 큐 사이의 순서는 보장되지 않는다.
- **"마이크로태스크는 한 바퀴에 하나씩 실행된다"** — 마이크로태스크 큐는 빌 때까지 전부 실행된다. 그래서 마이크로태스크가 계속 새 마이크로태스크를 예약하면 태스크도 렌더링도 영원히 실행되지 못하고 페이지가 멈춘다.
- **"async/await를 쓰면 다른 스레드에서 실행된다"** — `await` 이후의 코드도 같은 스레드에서 마이크로태스크로 이어서 실행된다. 병렬 실행이 아니다.
- **"Node.js와 브라우저의 이벤트 루프는 같다"** — 큰 원칙은 비슷하지만 Node.js에는 `process.nextTick`, `setImmediate`, 단계(phase) 같은 고유 규칙이 있다. 세부 순서는 Node.js 문서를 기준으로 판단하자.
