## 왜 필요한가?

일정 관리 서비스를 만든다고 해 보자. 사용자의 Google 캘린더 일정을 가져와 보여 주고 싶다. 가장 단순한 방법은 사용자에게 **Google 아이디와 비밀번호를 직접 입력받아** 대신 로그인하는 것이다. 하지만 이 방법에는 심각한 문제가 있다.

- 우리 서비스가 비밀번호를 **저장하거나 유출**할 수 있다. 사용자는 이를 통제할 수 없다.
- 캘린더만 필요한데 메일, 드라이브까지 **모든 권한**을 갖게 된다.
- 사용자가 우리 서비스의 접근만 **취소**하려면 Google 비밀번호를 바꾸는 수밖에 없다. 그러면 다른 모든 서비스도 함께 끊긴다.
- Google 쪽에서 2단계 인증 같은 보호 수단을 적용하기 어렵다.

OAuth 2.0은 이 문제를 **"비밀번호 대신, 범위와 기한이 제한된 토큰을 발급받아 쓰게 하자"** 는 방식으로 해결한다. 사용자는 Google(인가 서버)에 직접 로그인해 "이 서비스에 캘린더 읽기 권한을 주겠다"고 동의하고, 우리 서비스는 그 결과로 **액세스 토큰**만 받는다. 비밀번호는 우리 서비스를 거치지 않는다.

## 쉽게 이해하는 비유

**호텔 발레파킹 키**를 떠올려 보자. 일부 고급 차량에는 주차 요원에게 맡기는 전용 키가 있다. 이 키로는 시동을 걸고 짧은 거리를 운전할 수 있지만 트렁크나 글러브박스는 열 수 없다.

- 차 주인(**리소스 소유자**)은 마스터 키(비밀번호)를 넘기지 않는다.
- 주차 요원(**클라이언트**)은 제한된 기능만 있는 발레 키(**액세스 토큰**)를 받는다.
- 키를 만들어 주는 곳(**인가 서버**)과 실제로 그 키로 열리는 차(**리소스 서버**)는 따로 있을 수 있다.
- 발레 키를 회수해도 마스터 키는 그대로다(토큰 폐기는 비밀번호에 영향이 없다).

Authorization Code 흐름은 여기에 한 단계를 더한다. 주차 요원이 키를 바로 받는 게 아니라 **번호표(인가 코드)** 를 먼저 받고, 직원 전용 창구(토큰 엔드포인트)에서 신분을 확인받은 뒤 번호표를 키로 바꾼다. 번호표는 손님 손(브라우저)을 거치지만 키는 거치지 않는다.

비유가 틀리는 지점도 있다. 발레 키는 기능이 물리적으로 고정되어 있지만, OAuth 토큰의 권한 범위(scope)는 요청과 사용자 동의에 따라 매번 달라질 수 있고, 만료 시간이 있어 시간이 지나면 저절로 쓸 수 없게 된다.

## 동작 원리

### 네 가지 역할

RFC 6749는 다음 네 역할을 정의한다.

| 역할 | 설명 | 예 |
| --- | --- | --- |
| 리소스 소유자 (Resource Owner) | 보호된 리소스에 대한 접근을 허락할 수 있는 주체. 보통 최종 사용자 | 캘린더 주인인 사용자 |
| 클라이언트 (Client) | 리소스 소유자의 허락을 받아 리소스에 접근하려는 애플리케이션 | 우리 일정 관리 서비스 |
| 인가 서버 (Authorization Server) | 사용자를 인증하고 동의를 받은 뒤 토큰을 발급 | Google 계정 서버, Keycloak |
| 리소스 서버 (Resource Server) | 보호된 리소스를 갖고 있고, 액세스 토큰을 검증해 요청을 처리 | Google Calendar API |

인가 서버와 리소스 서버는 같은 서비스가 운영할 수도, 완전히 다른 서버일 수도 있다.

클라이언트는 비밀을 안전하게 보관할 수 있는지에 따라 둘로 나뉜다.

- **기밀 클라이언트(Confidential Client)**: 서버에서 실행되는 웹 애플리케이션처럼 `client_secret`을 사용자에게 노출하지 않고 보관할 수 있다.
- **공개 클라이언트(Public Client)**: 브라우저에서 실행되는 SPA, 모바일·데스크톱 앱처럼 코드가 사용자 기기에 배포되어 **비밀을 숨길 수 없다**. 이런 클라이언트에 `client_secret`을 넣으면 누구나 추출할 수 있으므로 비밀로서 의미가 없다.

### Authorization Code 흐름

1. **인가 요청**: 클라이언트가 사용자를 인가 서버의 authorization endpoint로 리다이렉트한다. 이때 `response_type=code`, `client_id`, `redirect_uri`, `scope`, `state`, PKCE의 `code_challenge`를 쿼리 파라미터로 보낸다.
2. **사용자 인증과 동의**: 사용자는 **인가 서버의 화면에서** 로그인하고, 요청된 권한에 동의한다. 클라이언트는 이 과정에서 비밀번호를 보지 못한다.
3. **인가 코드 전달**: 인가 서버가 브라우저를 `redirect_uri`로 리다이렉트하며 `code`와 `state`를 붙인다. 인가 코드는 수명이 짧고(RFC 6749는 최대 10분을 권장) **한 번만** 쓸 수 있어야 한다.
4. **토큰 교환**: 클라이언트가 **백엔드 채널(서버 간 HTTP 요청)** 로 token endpoint에 `code`, `redirect_uri`, `code_verifier`를 보내고, 기밀 클라이언트라면 `client_secret` 등으로 자신을 인증한다.
5. **토큰 발급**: 인가 서버가 검증을 마치면 액세스 토큰(필요하면 리프레시 토큰)을 응답한다.
6. **리소스 접근**: 클라이언트는 `Authorization: Bearer <액세스 토큰>` 헤더로 리소스 서버를 호출한다.

왜 토큰을 바로 주지 않고 코드를 거칠까? 3단계의 리다이렉트 URL은 브라우저 주소창, 방문 기록, 프록시 로그, `Referer` 헤더 등으로 **새어 나갈 수 있는 경로**다. 그 경로에는 단독으로는 쓸모없는 일회용 코드만 싣고, 실제 토큰은 클라이언트 인증과 PKCE 검증을 거친 서버 간 요청으로만 받게 하는 것이다.

### state: CSRF 방어

공격자가 **자신의** 인가 코드가 담긴 콜백 URL(`/callback?code=공격자의코드`)을 피해자의 브라우저가 열게 만들면, 피해자의 세션이 공격자 계정에 연결될 수 있다. 피해자가 이후 입력한 정보가 공격자 계정에 저장되는 식이다.

이를 막기 위해 클라이언트는 인가 요청 전에 **예측할 수 없는 값**을 만들어 사용자 세션에 저장하고 `state` 파라미터로 함께 보낸다. 콜백에서 돌아온 `state`가 세션의 값과 다르면 요청을 거부한다. 공격자는 피해자 세션에 저장된 값을 알 수 없으므로 위조된 콜백이 통과하지 못한다.

RFC 9700은 PKCE나 OpenID Connect의 `nonce`로 CSRF를 막을 수 있다면 그것도 허용하지만, 그렇지 않다면 `state`에 담긴 일회용 CSRF 토큰을 반드시 쓰라고 한다. 실무에서는 대개 `state`와 PKCE를 함께 쓴다.

### PKCE: 가로챈 코드를 무력화

PKCE(Proof Key for Code Exchange, RFC 7636, "픽시"라고 읽는다)는 **인가 코드를 가로채도 토큰으로 바꿀 수 없게** 만드는 확장이다. 원래 `client_secret`이 없는 공개 클라이언트(모바일 앱 등)를 위해 만들어졌다.

1. 클라이언트가 매 요청마다 무작위 문자열 **`code_verifier`** 를 만든다. 43~128자의 URL 안전 문자(`A-Z`, `a-z`, `0-9`, `-`, `.`, `_`, `~`)로, 32바이트 난수를 base64url 인코딩하는 방법이 권장된다.
2. 이를 해시한 **`code_challenge`** 를 만든다. `S256` 방식은 `BASE64URL(SHA256(code_verifier))`다.
3. **인가 요청**에는 `code_challenge`와 `code_challenge_method=S256`만 보낸다. 인가 서버는 이 값을 발급할 코드와 연결해 둔다.
4. **토큰 요청**에는 원본 `code_verifier`를 보낸다. 인가 서버는 이를 해시해 저장해 둔 `code_challenge`와 비교한다.

공격자가 리다이렉트 과정에서 코드를 가로채더라도, `code_verifier`는 브라우저를 거친 적이 없으므로 알 수 없다. 해시에서 원본을 거꾸로 계산할 수도 없다. `plain` 방식(챌린지 = 검증자 원문)도 스펙에 있지만, 인가 요청에서 원문이 노출되므로 `S256`을 써야 한다.

RFC 9700은 공개 클라이언트에는 PKCE를 **필수**로, 기밀 클라이언트에도 **권장**한다. `client_secret`이 있어도 인가 코드 주입(authorization code injection) 같은 공격을 막는 데 도움이 되기 때문이다.

### 액세스 토큰과 리프레시 토큰

| 구분 | 액세스 토큰 | 리프레시 토큰 |
| --- | --- | --- |
| 용도 | 리소스 서버에 API 요청할 때 제시 | 액세스 토큰이 만료되면 새 토큰을 발급받을 때 사용 |
| 보내는 곳 | 리소스 서버 | 인가 서버의 token endpoint만 |
| 수명 | 짧다 (분~시간 단위가 흔하다) | 길다 (발급 여부와 수명은 인가 서버 정책) |
| 형식 | OAuth 2.0은 규정하지 않는다. 불투명한 문자열일 수도, JWT일 수도 있다 | 마찬가지로 인가 서버가 정한다 |

액세스 토큰을 짧게 유지하면 유출되어도 피해 기간이 짧다. 리프레시 토큰은 더 강력하므로 더 엄격하게 보관한다. RFC 9700은 공개 클라이언트의 리프레시 토큰을 **송신자 제약(sender-constrained)** 하거나 **사용할 때마다 새로 교체(rotation)** 하라고 권고한다.

### OAuth 2.0은 "로그인" 프로토콜이 아니다

OAuth 2.0은 **인가(Authorization)**, 즉 "이 클라이언트가 무엇에 접근해도 되는가"를 다루는 프레임워크다. 액세스 토큰은 리소스 서버를 위한 것이고, 클라이언트가 토큰을 열어 "누가 로그인했는가"를 판단하라고 만든 것이 아니다. 실제로 액세스 토큰만으로 사용자를 식별하는 방식은 다른 클라이언트용으로 발급된 토큰을 들고 와 로그인하는 공격에 취약할 수 있다.

**인증(Authentication)**, 즉 "로그인"을 표준화한 것은 OAuth 2.0 위에 얹은 **OpenID Connect(OIDC)** 다.

- 인가 요청의 `scope`에 `openid`를 포함하면 OIDC 요청이 된다.
- 토큰 응답에 **ID Token**이 추가된다. ID Token은 서명된 JWT로, 발급자(`iss`), 사용자 식별자(`sub`), 대상 클라이언트(`aud`), 만료(`exp`), 발급 시각(`iat`) 등을 담는다.
- 클라이언트는 서명과 `iss`·`aud`·`exp`를 검증하고, 요청 때 보낸 `nonce`가 있다면 그것도 일치하는지 확인한다. `aud`에 자신의 `client_id`가 있어야 하므로 다른 클라이언트용 토큰을 재사용할 수 없다.

"Google로 로그인", "카카오로 로그인" 같은 소셜 로그인은 대부분 OIDC(또는 제공자별 사용자 정보 API)를 이용한다.

### 더 이상 권장하지 않는 그랜트

- **Implicit Grant** (`response_type=token`): 토큰을 리다이렉트 URL의 프래그먼트로 브라우저에 바로 전달한다. 원래 백엔드 없는 SPA를 위해 만들었지만, 토큰이 브라우저 기록 등으로 유출되기 쉽고 클라이언트를 확인할 방법이 없다. RFC 9700은 Implicit Grant를 쓰지 말고(SHOULD NOT) Authorization Code + PKCE를 쓰라고 권고한다.
- **Resource Owner Password Credentials Grant**: 클라이언트가 사용자 비밀번호를 직접 받아 토큰으로 바꾼다. OAuth를 쓰는 이유 자체를 부정하는 방식이라 RFC 9700은 사용을 금지(MUST NOT)한다.

### HTTP 메시지로 보는 흐름

인가 요청(브라우저가 인가 서버로 이동하는 URL, 가독성을 위해 줄바꿈):

```http
GET /authorize?response_type=code
    &client_id=my-client
    &redirect_uri=https%3A%2F%2Fapp.example.com%2Flogin%2Foauth2%2Fcode%2Fmy-idp
    &scope=openid%20profile%20email
    &state=af0ifjsldkj
    &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
    &code_challenge_method=S256 HTTP/1.1
Host: auth.example.com
```

인가 서버의 응답(사용자 동의 후):

```http
HTTP/1.1 302 Found
Location: https://app.example.com/login/oauth2/code/my-idp?code=SplxlOBeZQQYbYS6WxSbIA&state=af0ifjsldkj
```

```http
&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https%3A%2F%2Fapp.example.com%2Flogin%2Foauth2%2Fcode%2Fmy-idp
```

```json
{
  "access_token": "SlAV32hkKG",
  "token_type": "Bearer",
```

`code_verifier`와 `code_challenge` 값은 RFC 7636 부록 B의 예시이고, 나머지 토큰 값은 설명용이다.

### PKCE 값 만들기 (Java)

프레임워크가 대신 처리해 주는 경우가 많지만, 원리를 확인하기 위해 직접 만들어 보면 다음과 같다.

```java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.security.SecureRandom;
import java.util.Base64;

public final class Pkce {
    private static final SecureRandom RANDOM = new SecureRandom();
    private static final Base64.Encoder B64URL = Base64.getUrlEncoder().withoutPadding();

    // 32바이트 난수 → base64url(패딩 없음) = 43자
    public static String newCodeVerifier() {
        byte[] bytes = new byte[32];
        RANDOM.nextBytes(bytes);
        return B64URL.encodeToString(bytes);
    }

    // S256: BASE64URL(SHA256(ASCII(code_verifier)))
    public static String codeChallenge(String codeVerifier) throws NoSuchAlgorithmException {
        byte[] hash = MessageDigest.getInstance("SHA-256")
                .digest(codeVerifier.getBytes(StandardCharsets.US_ASCII));
        return B64URL.encodeToString(hash);
    }

    public static void main(String[] args) throws Exception {
        // RFC 7636 부록 B의 예시 값으로 검증
        String challenge = codeChallenge("dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk");
        System.out.println(challenge.equals("E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM")); // true
    }
}
```

### Spring Security로 OAuth2 로그인 구성

`spring-boot-starter-oauth2-client` 의존성을 추가하면, Spring Security가 인가 요청 생성, `state` 생성·검증, 코드 교환, 사용자 정보 조회까지 처리한다.

```yaml
# application.yml
spring:
  security:
    oauth2:
      client:
        registration:
          google:
            client-id: ${GOOGLE_CLIENT_ID}
            client-secret: ${GOOGLE_CLIENT_SECRET}
            # scope를 생략하면 Google의 기본값(openid, profile, email)이 쓰인다
```

`google`, `github` 같은 등록 id는 `CommonOAuth2Provider`에 authorization-uri, token-uri 등이 미리 정의되어 있어 `client-id`와 `client-secret`만 넣으면 된다. 기본 리다이렉트 URI는 `{baseUrl}/login/oauth2/code/{registrationId}`이므로, 로컬에서는 Google 콘솔에 `http://localhost:8080/login/oauth2/code/google`을 등록한다. `client-secret`은 코드나 저장소에 넣지 말고 환경 변수나 비밀 관리 도구로 주입한다.

```java
import static org.springframework.security.config.Customizer.withDefaults;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(authorize -> authorize
                .requestMatchers("/", "/error").permitAll()
                .anyRequest().authenticated()
            )
            // /oauth2/authorization/{registrationId}로 인가 요청을 시작하고
            // /login/oauth2/code/{registrationId}에서 코드를 받아 토큰으로 교환한다
            .oauth2Login(withDefaults());
        return http.build();
    }
}
```

```java
import java.util.Map;

import org.springframework.security.core.annotation.AuthenticationPrincipal;
import org.springframework.security.oauth2.core.oidc.user.OidcUser;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class MeController {

    // openid scope로 로그인하면 principal은 ID Token 정보를 담은 OidcUser다
    @GetMapping("/me")
    public Map<String, Object> me(@AuthenticationPrincipal OidcUser user) {
        return Map.of(
                "sub", user.getSubject(),
                "name", user.getFullName(),
                "email", user.getEmail()
        );
    }
}
```

OIDC를 지원하지 않는 제공자(예: GitHub)로 로그인하면 principal은 `OidcUser`가 아니라 `OAuth2User`가 된다. 이 경우 Spring Security는 사용자 정보 엔드포인트를 호출해 속성을 채운다.

Spring Security의 PKCE 적용 방식은 버전에 따라 다르다. 현재 레퍼런스는 `client-secret`이 없고 `client-authentication-method: none`인 공개 클라이언트에 PKCE를 자동 적용하며, 등록 정보의 `clientSettings.requireProofKey`로 제어한다고 설명한다. 사용하는 버전의 문서에서 기밀 클라이언트의 기본 동작을 확인하자.

## 언제 사용해야 할까?

| 상황 | 권장 방식 |
| --- | --- |
| 서버 렌더링 웹앱, BFF가 있는 SPA (기밀 클라이언트) | Authorization Code + `client_secret` 등 클라이언트 인증 + PKCE |
| 백엔드 없는 SPA, 모바일·데스크톱 앱 (공개 클라이언트) | Authorization Code + PKCE (secret 없음) |
| "Google로 로그인"처럼 사용자 로그인이 목적 | OpenID Connect (`openid` scope, ID Token 검증) |
| 사용자 없이 서버끼리 API 호출 (배치, 마이크로서비스) | Client Credentials Grant |
| 키보드 입력이 어려운 기기 (TV, CLI) | Device Authorization Grant (RFC 8628) |
| 외부 서비스에 사용자 비밀번호를 받아 대신 로그인 | 쓰지 않는다 (Password Grant 금지) |

- **우리 서비스 자체의 로그인**만 필요하고 외부 계정 연동이 없다면 OAuth를 꼭 쓸 필요는 없다. 일반적인 세션 로그인으로 충분할 수 있다.
- SPA라면 토큰을 브라우저 저장소에 두지 않고 **BFF(Backend for Frontend)** 서버가 토큰을 보관하고 브라우저와는 세션 쿠키로 통신하는 구조가 많이 쓰인다. 위의 Spring 예시가 이 형태다.

## 주의 사항과 흔한 오해

- **"OAuth로 로그인한다"** — 엄밀히 말해 OAuth 2.0은 인가 위임 프레임워크이고, 로그인(인증)은 OpenID Connect가 정의한다. 액세스 토큰을 받았다는 사실만으로 사용자를 식별하지 말고, ID Token을 검증하거나 검증된 라이브러리(Spring Security 등)에 맡기자.
- **"PKCE가 있으면 `state`는 필요 없다"** — RFC 9700은 PKCE가 CSRF 방어 역할도 할 수 있다고 보지만, 인가 서버가 PKCE를 실제로 지원·강제하는지 확인할 수 있을 때의 이야기다. 대부분의 라이브러리는 둘 다 사용하며, 직접 구현한다면 둘 다 쓰는 것이 안전하다.
- **"SPA에 `client_secret`을 넣으면 기밀 클라이언트가 된다"** — 브라우저나 앱에 배포된 비밀은 누구나 꺼낼 수 있다. `client_secret`은 서버처럼 비밀을 보관할 수 있는 기밀 클라이언트에만 둔다.
- **"Implicit Grant는 SPA용 표준 방식이다"** — 과거에는 그랬지만, 현재 RFC 9700은 사용하지 말라고 권고한다. SPA도 Authorization Code + PKCE를 쓴다.
- **`redirect_uri`는 정확히 일치하도록 등록한다.** 와일드카드나 느슨한 패턴 매칭은 코드를 공격자 주소로 보내는 공격에 악용될 수 있다. RFC 9700은 인가 서버가 정확한 문자열 비교를 하도록 요구한다(네이티브 앱의 localhost 포트 등 예외 제외).
- **`scope`는 필요한 만큼만 요청한다.** 권한을 넓게 요청할수록 토큰 유출 시 피해가 커지고, 사용자 동의도 받기 어렵다.
- **JWT 액세스 토큰을 클라이언트가 해석하지 않는다.** 액세스 토큰의 형식과 내용은 인가 서버와 리소스 서버 사이의 약속이다. 클라이언트는 불투명한 문자열로 다루는 것이 원칙이다.
