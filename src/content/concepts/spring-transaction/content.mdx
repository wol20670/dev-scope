## 왜 필요한가?

주문을 처리할 때 세 가지 일을 한다고 해 보자.

1. 주문 행을 저장한다.
2. 상품 재고를 줄인다.
3. 회원 포인트를 차감한다.

3번에서 "포인트 부족"으로 실패했는데 1, 2번은 이미 DB에 반영되었다면, 결제되지 않은 주문이 생기고 재고만 줄어든다. 세 작업은 **모두 성공하거나 모두 취소되어야** 한다. 이것이 트랜잭션의 원자성이다.

JDBC로 직접 처리하면 이런 코드가 된다.

```java
Connection conn = dataSource.getConnection();
try {
    conn.setAutoCommit(false);
    orderDao.insert(conn, order);      // 같은 트랜잭션을 쓰려면
    productDao.decrease(conn, ...);    // 같은 커넥션을 계속 넘겨야 한다
    pointDao.use(conn, ...);
    conn.commit();
} catch (Exception e) {
    conn.rollback();
    throw e;
} finally {
    conn.close();
}
```

비즈니스 로직보다 트랜잭션 처리 코드가 더 길고, 모든 메서드가 커넥션을 파라미터로 주고받아야 한다. 데이터 접근 기술을 JDBC에서 JPA로 바꾸면 이 코드도 전부 바뀐다.

Spring은 이 문제를 두 단계로 해결한다.

- **트랜잭션 추상화**: `PlatformTransactionManager`라는 공통 인터페이스 뒤에 JDBC, JPA 등 기술별 구현을 숨긴다.
- **선언적 트랜잭션**: 메서드에 `@Transactional`만 붙이면, 시작·커밋·롤백 코드를 Spring이 메서드 바깥에서 대신 실행한다.

## 쉽게 이해하는 비유

**비서를 둔 계약 담당자**를 떠올려 보자.

외부 사람이 담당자에게 일을 맡기려면 항상 **비서**를 거친다. 비서는 일이 시작되기 전에 "임시 장부"를 펼치고, 담당자가 일을 무사히 끝내면 장부를 정식으로 확정(커밋)한다. 도중에 심각한 문제가 생기면 임시 장부를 찢어 버린다(롤백). 담당자는 자기 업무에만 집중한다.

여기서 비서가 Spring이 만든 **프록시**다. 이 비유는 흔한 함정도 잘 보여 준다. 담당자가 **자기 책상에서 혼잣말로** 다른 업무를 시작하면(같은 객체 안의 `this.method()` 호출) 비서는 그 사실을 모른다. 그러니 새 장부도 펼쳐지지 않는다.

비유가 틀리는 지점도 있다. 실제 "장부"는 DB 커넥션 위의 트랜잭션이고, 비서는 사람이 아니라 메서드 호출을 가로채는 객체라서 호출할 때마다 따로 판단하지 않고 **애너테이션에 적힌 규칙을 그대로 적용**한다.

## 동작 원리

### 프록시가 메서드 호출을 감싼다

`@Transactional`이 붙은 빈은 컨테이너에 **원본 대신 프록시**로 등록된다. 다른 빈이 주입받는 것도 이 프록시다. 프록시는 인터페이스가 있으면 JDK 동적 프록시, 없으면 CGLIB로 만든 하위 클래스다(Spring Boot는 기본으로 CGLIB 방식을 사용한다).

호출 흐름은 다음과 같다.

1. 호출자가 `orderService.place()`를 부른다. 실제로는 프록시의 메서드가 불린다.
2. 프록시 안의 `TransactionInterceptor`가 메서드의 트랜잭션 속성(전파, 격리 수준, readOnly 등)을 읽는다.
3. 트랜잭션 매니저에 트랜잭션을 요청한다. 새 트랜잭션이라면 보통 커넥션을 얻어 자동 커밋을 끄고, 그 커넥션(JPA라면 `EntityManager`)을 **현재 스레드에 묶어 둔다.**
4. 원본 객체의 메서드가 실행된다. 그 안에서 쓰는 리포지토리들은 스레드에 묶인 같은 커넥션을 사용하므로, 커넥션을 파라미터로 넘길 필요가 없다.
5. 메서드가 정상 반환하면 커밋하고, 예외가 나면 **롤백 규칙**에 따라 롤백 또는 커밋한 뒤 예외를 다시 던진다.

트랜잭션이 스레드에 묶이기 때문에, 메서드 안에서 **새 스레드나 `@Async`로 넘긴 작업은 같은 트랜잭션에 참여하지 않는다.**

### 롤백 규칙: 모든 예외가 롤백되지는 않는다

기본 설정에서는 다음과 같다.

| 메서드 밖으로 나간 예외 | 결과 |
| --- | --- |
| `RuntimeException`과 그 하위 클래스 (언체크 예외) | 롤백 |
| `Error` | 롤백 |
| 체크 예외 (`Exception`의 하위 중 `RuntimeException`이 아닌 것, 예: `IOException`) | **커밋** |

체크 예외까지 롤백하려면 `@Transactional(rollbackFor = Exception.class)`처럼 롤백 규칙을 지정한다. 반대로 특정 언체크 예외는 커밋하고 싶다면 `noRollbackFor`를 쓴다. Spring Framework 6.2부터는 `@EnableTransactionManagement(rollbackOn = ALL_EXCEPTIONS)`로 애플리케이션 전체의 기본값을 "모든 예외 롤백"으로 바꿀 수도 있다.

중요한 점은 프록시가 **메서드 밖으로 던져진 예외만 본다**는 것이다. 메서드 안에서 `try-catch`로 예외를 삼키고 정상 반환하면, 프록시는 성공으로 판단해 커밋한다.

### 전파(Propagation): 이미 트랜잭션이 있으면?

트랜잭션 메서드가 다른 트랜잭션 메서드를 호출할 때 어떻게 할지를 정한다.

| 전파 속성 | 기존 트랜잭션이 있을 때 | 없을 때 |
| --- | --- | --- |
| `REQUIRED` (기본값) | 참여한다 | 새로 시작 |
| `REQUIRES_NEW` | 기존 것과 별개의 새 트랜잭션을 시작 | 새로 시작 |
| `NESTED` | 같은 트랜잭션 안에 세이브포인트를 만든다 | 새로 시작 |
| `SUPPORTS` | 참여한다 | 트랜잭션 없이 실행 |
| `MANDATORY` | 참여한다 | 예외 |
| `NOT_SUPPORTED` | 기존 것을 보류하고 트랜잭션 없이 실행 | 트랜잭션 없이 실행 |
| `NEVER` | 예외 | 트랜잭션 없이 실행 |

**`REQUIRED`의 함정**: 안쪽 메서드가 참여한 경우, 바깥과 안쪽은 논리적으로는 각자의 범위지만 **물리적으로는 같은 트랜잭션**이다. 안쪽 메서드에서 롤백 대상 예외가 나면 트랜잭션 전체가 "롤백 전용(rollback-only)"으로 표시된다. 바깥 메서드가 그 예외를 `catch`하고 정상 종료해도 커밋할 수 없으므로, Spring은 롤백하고 `UnexpectedRollbackException`을 던져 "커밋된 줄 알았는데 아니었다"는 상황을 알린다.

**`REQUIRES_NEW`**: 독립된 물리 트랜잭션이므로 커밋·롤백이 따로 일어난다. 실패해도 남겨야 하는 감사 로그 등에 쓴다. 다만 바깥 트랜잭션의 커넥션을 쥔 채 **커넥션을 하나 더** 얻으므로, 동시 요청이 많으면 커넥션 풀이 고갈되어 교착 상태에 빠질 수 있다. Spring 레퍼런스도 커넥션 풀 크기가 동시 스레드 수보다 충분히 크지 않다면 쓰지 말라고 경고한다.

**`NESTED`**: JDBC 세이브포인트를 사용하므로 `DataSourceTransactionManager` 같은 JDBC 기반 트랜잭션에서 동작한다. JPA 트랜잭션 매니저에서는 지원 여부가 구현과 설정에 따라 다르다.

### readOnly

`@Transactional(readOnly = true)`는 "이 트랜잭션은 읽기만 한다"는 **힌트**다.

- JDBC 드라이버에 읽기 전용 힌트가 전달되어 DB나 드라이버가 최적화할 수 있다.
- Hibernate를 쓰면 Spring이 플러시 모드를 `MANUAL`로 설정한다. 커밋 시 변경 감지(dirty checking)와 플러시를 하지 않으므로, 큰 객체 그래프를 읽을 때 비용이 줄어든다.
- 쓰기를 **막아 준다는 보장은 없다.** 일부 DB는 읽기 전용 트랜잭션 안의 `INSERT`/`UPDATE`를 거부하지만, 그렇지 않은 DB도 있다.

Spring Data JPA의 기본 리포지토리(`SimpleJpaRepository`)는 조회 메서드에 이미 `readOnly = true`를 적용해 둔다.

### 그 밖의 속성

- `isolation`: 격리 수준. 기본값 `DEFAULT`는 DB의 기본 격리 수준을 따른다.
- `timeout`: 트랜잭션 제한 시간(초).
- 참여하는 안쪽 트랜잭션(`REQUIRED`로 기존 트랜잭션에 참여)은 자신의 격리 수준, timeout, readOnly 설정을 **기본적으로 무시**한다. 이 설정들은 트랜잭션을 실제로 시작하는 쪽에서만 의미가 있다.

## 코드 예시

### 기본 사용

```java
@Service
public class OrderService {

    private final OrderRepository orderRepository;
    private final ProductRepository productRepository;
    private final PointService pointService;

    public OrderService(OrderRepository orderRepository,
                        ProductRepository productRepository,
                        PointService pointService) {
        this.orderRepository = orderRepository;
        this.productRepository = productRepository;
        this.pointService = pointService;
    }

    @Transactional // org.springframework.transaction.annotation.Transactional
    public Long place(Long memberId, Long productId, int quantity) {
        Product product = productRepository.findById(productId).orElseThrow();
        product.decrease(quantity);                       // 변경 감지로 UPDATE
        pointService.use(memberId, product.totalPrice(quantity)); // REQUIRED → 같은 트랜잭션에 참여
        return orderRepository.save(new Order(memberId, productId, quantity)).getId();
        // 어디서든 RuntimeException이 나면 세 작업이 모두 롤백된다
    }
}
```

### 체크 예외도 롤백하기

```java
@Transactional(rollbackFor = Exception.class)
public void importOrders(Path csv) throws IOException {
    for (String line : Files.readAllLines(csv)) {   // IOException은 체크 예외
        orderRepository.save(Order.parse(line));
    }
    // rollbackFor가 없으면 IOException이 나도 이미 저장한 행이 커밋된다
}
```

### 자기 호출 문제와 해결

```java
@Service
public class BulkOrderService {

    // 잘못된 예: place()의 @Transactional이 적용되지 않는다
    public void placeAll(List<OrderCommand> commands) {
        for (OrderCommand c : commands) {
            this.place(c); // 프록시를 거치지 않는 내부 호출
        }
    }

    @Transactional
    public void place(OrderCommand command) { /* ... */ }
}
```

가장 단순하고 레퍼런스에서도 권장하는 해결책은 **자기 호출이 생기지 않게 구조를 바꾸는 것**이다. 트랜잭션 메서드를 다른 빈으로 분리하면 호출이 프록시를 거친다.

```java
@Service
public class BulkOrderService {

    private final OrderService orderService; // 프록시가 주입된다

    public BulkOrderService(OrderService orderService) {
        this.orderService = orderService;
    }

    public void placeAll(List<OrderCommand> commands) {
        for (OrderCommand c : commands) {
            orderService.place(c); // 주문마다 별도 트랜잭션으로 커밋·롤백
        }
    }
}
```

### 실패해도 남겨야 하는 로그: `REQUIRES_NEW`

```java
@Service
public class AuditLogService {

    private final AuditLogRepository auditLogRepository;

    public AuditLogService(AuditLogRepository auditLogRepository) {
        this.auditLogRepository = auditLogRepository;
    }

    // 호출한 쪽 트랜잭션이 롤백되어도 이 로그는 독립적으로 커밋된다
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void record(String action, Long targetId) {
        auditLogRepository.save(new AuditLog(action, targetId));
    }
}
```

### 조회 전용 서비스

```java
@Service
@Transactional(readOnly = true) // 클래스의 모든 public 메서드에 기본 적용
public class ProductQueryService {

    private final ProductRepository productRepository;

    public ProductQueryService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    public ProductResponse find(Long id) {
        return ProductResponse.from(productRepository.findById(id).orElseThrow());
    }

    @Transactional // 메서드에 붙인 설정이 우선한다 (readOnly = false)
    public void rename(Long id, String name) {
        productRepository.findById(id).orElseThrow().rename(name);
    }
}
```

## 언제 사용해야 할까?

**어디에 붙일까?** 보통 하나의 유스케이스(주문하기, 회원 가입 등)를 담당하는 **서비스 계층의 public 메서드**에 붙인다. 컨트롤러에 붙이면 HTTP 처리까지 트랜잭션이 길어지고, 리포지토리 메서드 하나하나에만 의존하면 여러 리포지토리 호출을 하나로 묶을 수 없다.

| 상황 | 선택 |
| --- | --- |
| 여러 쓰기 작업이 함께 성공·실패해야 한다 | `@Transactional` (기본 `REQUIRED`) |
| 조회만 한다 | `@Transactional(readOnly = true)` |
| 바깥이 실패해도 반드시 남겨야 한다 (감사 로그, 실패 기록) | `REQUIRES_NEW` (커넥션 풀 여유 확인) |
| 일부만 되돌리고 나머지는 계속 진행 | JDBC 기반이면 `NESTED` 고려, 아니면 트랜잭션을 나눠 설계 |
| 체크 예외로 실패를 알리는 메서드 | `rollbackFor`를 명시하거나 언체크 예외로 감싸기 |
| 외부 API 호출, 파일 업로드 등 느린 작업 | 트랜잭션 **밖으로** 빼서 트랜잭션을 짧게 유지 |

## 주의 사항과 흔한 오해

- **"`@Transactional`을 붙이면 어디서 호출하든 트랜잭션이 걸린다"** — 프록시를 거친 **외부 호출**에만 적용된다. 같은 클래스 안의 `this.method()` 호출은 트랜잭션이 시작되지 않는다. 같은 이유로 `@PostConstruct` 같은 초기화 코드에서 호출해도 프록시가 아직 완성되지 않아 기대대로 동작하지 않을 수 있다.
- **"예외가 나면 무조건 롤백된다"** — 기본 설정에서 체크 예외는 **커밋**된다. 또한 예외를 `catch`해서 삼키면 프록시는 성공으로 본다.
- **"안쪽 메서드의 예외를 잡았으니 바깥은 커밋된다"** — `REQUIRED`로 참여한 안쪽 메서드가 롤백 대상 예외를 던지면 트랜잭션 전체가 rollback-only가 된다. 바깥에서 잡아도 커밋되지 않고 `UnexpectedRollbackException`이 난다. 정말 따로 처리해야 한다면 트랜잭션 경계를 나누자.
- **메서드 접근 제어자**: `@Transactional`은 보통 `public` 메서드에 붙인다. Spring Framework 6.0부터는 클래스 기반(CGLIB) 프록시에서 `protected`와 패키지 접근 메서드도 지원하지만, `private` 메서드와 `final` 메서드는 프록시가 가로챌 수 없다. 인터페이스 기반 프록시라면 인터페이스에 선언된 `public` 메서드여야 한다.
- **"readOnly면 쓰기가 막힌다"** — 힌트일 뿐이다. 실제로 쓰기가 거부되는지는 DB와 드라이버에 따라 다르다. 또 Hibernate에서는 플러시가 생략되므로, 엔티티를 수정해도 DB에 반영되지 않아 혼란을 줄 수 있다.
- **트랜잭션 안에서 오래 걸리는 작업을 하지 말자.** 외부 API 응답을 기다리는 동안 커넥션과 잠금을 계속 쥐고 있어 커넥션 풀이 고갈되거나 다른 트랜잭션이 대기한다.
- **`@Async`나 새 스레드로 넘긴 작업은 트랜잭션이 이어지지 않는다.** 트랜잭션은 스레드에 묶여 있기 때문이다.
- **import를 확인하자.** Spring은 `jakarta.transaction.Transactional`도 인식하지만 `propagation`, `readOnly` 같은 속성 표현이 다르다. Spring 기능을 모두 쓰려면 `org.springframework.transaction.annotation.Transactional`을 사용한다.
- **테스트의 `@Transactional`은 다르게 동작한다.** Spring TestContext에서 테스트 메서드에 붙이면 기본적으로 테스트가 끝난 뒤 **롤백**된다. 그래서 테스트에서는 성공했는데 실제로는 커밋 시점(플러시, 제약 조건 검사)에 실패하는 경우를 놓칠 수 있다.
