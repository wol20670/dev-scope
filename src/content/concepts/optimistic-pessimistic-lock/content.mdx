## 왜 필요한가?

재고가 10개인 상품을 두 사용자가 **거의 동시에** 구매한다고 해 보자.

1. A가 재고를 읽는다 → 10
2. B도 재고를 읽는다 → 10
3. A가 3개를 사서 `10 - 3 = 7`을 저장한다.
4. B가 2개를 사서 `10 - 2 = 8`을 저장한다.

최종 재고는 5여야 하지만 8이 남는다. A의 변경이 B의 변경에 덮어써져 사라졌기 때문이다. 이것을 **갱신 손실(Lost Update)** 이라고 한다.

트랜잭션은 각자 원자적으로 동작하지만, "읽고 → 계산하고 → 쓰는" 사이에 다른 트랜잭션이 끼어드는 것까지 자동으로 막아 주지는 않는다(격리 수준과 DBMS에 따라 다르다). 그래서 애플리케이션이 **충돌을 어떻게 다룰지** 정해야 하고, 대표적인 두 전략이 낙관적 락과 비관적 락이다.

## 쉽게 이해하는 비유

**공유 문서 편집**을 떠올려 보자.

- **낙관적 락**은 위키 편집과 비슷하다. 누구나 자유롭게 편집 화면을 연다. 저장 버튼을 누를 때 "내가 처음 열었던 판(버전)이 아직 최신인가?"를 확인하고, 그사이 누가 먼저 저장했다면 "편집 충돌" 메시지를 보여 준다.
- **비관적 락**은 회의실 예약과 비슷하다. 들어가기 전에 문에 "사용 중" 팻말을 건다. 다른 사람은 팻말이 내려갈 때까지 밖에서 기다린다.

"충돌은 거의 안 일어날 거야"라고 **낙관**하면 먼저 작업하고 나중에 확인하고, "충돌이 일어날 거야"라고 **비관**하면 미리 잠근다.

## 동작 원리

### 낙관적 락 (Optimistic Locking)

테이블에 **버전 컬럼**을 두고, 수정할 때마다 버전을 1씩 올린다. JPA에서는 엔티티 필드에 `@Version`을 붙이면 된다.

1. 조회할 때 데이터와 함께 현재 버전(예: `version = 0`)을 읽는다.
2. 수정할 때 `WHERE` 조건에 **읽었던 버전**을 넣는다.

```sql
UPDATE product
   SET stock = 7, version = 1
 WHERE id = 1 AND version = 0;
```

3. 그사이 다른 트랜잭션이 먼저 수정해 버전이 바뀌었다면 `WHERE` 조건에 맞는 행이 없어 **수정된 행 수가 0**이 된다.
4. JPA 구현체는 이를 충돌로 판단하고 `OptimisticLockException`을 던진다. Spring에서는 보통 `ObjectOptimisticLockingFailureException`(`OptimisticLockingFailureException` 계열)으로 변환되어 전달된다.

데이터베이스 잠금을 오래 잡지 않으므로 대기가 없고 처리량이 좋다. 대신 **충돌이 나면 작업 전체가 실패**하므로, 재시도하거나 사용자에게 알려야 한다.

### 비관적 락 (Pessimistic Locking)

데이터를 읽는 시점에 **행 잠금(row lock)** 을 건다. JPA의 `LockModeType.PESSIMISTIC_WRITE`는 대부분의 DBMS에서 `SELECT ... FOR UPDATE`로 변환된다.

1. A가 `SELECT ... FOR UPDATE`로 행을 읽으며 배타적 행 잠금을 얻는다.
2. B가 같은 행에 `SELECT ... FOR UPDATE`(또는 `UPDATE`)를 시도하면 **충돌하는 잠금**이므로 A가 끝날 때까지 대기한다.
3. A가 커밋(또는 롤백)하면 잠금이 해제된다.
4. B가 잠금을 얻고, **A가 커밋한 최신 값**을 기준으로 작업을 이어 간다.

<Callout type="warn" title="모든 읽기가 막히는 것은 아니다">
`FOR UPDATE`가 막는 것은 **충돌하는 잠금 요청과 수정**이다. PostgreSQL이나 MySQL InnoDB처럼 MVCC를 쓰는 DBMS에서는 잠금 없는 일반 `SELECT`가 대기 없이 커밋된 스냅샷을 읽는다. 반면 일부 DBMS·격리 수준(예: 잠금 기반 구현의 `SERIALIZABLE`)에서는 읽기도 대기할 수 있다. 사용하는 DBMS 문서를 꼭 확인하자.
</Callout>

## 시각화

아래에서 두 시나리오를 단계별로 실행해 보자. 재고 10개짜리 상품을 트랜잭션 A는 3개, B는 2개 구매한다. 최종 재고가 5가 되는지, 그 과정에서 무엇이 대기하고 무엇이 실패하는지 확인해 보자.

## 코드 예시

### 낙관적 락: `@Version`과 재시도

```java
@Entity
public class Product {
    @Id @GeneratedValue
    private Long id;

    private int stock;

    @Version // 수정 시 자동으로 증가하고, UPDATE ... WHERE version = ? 조건에 사용된다
    private Long version;

    public void decrease(int quantity) {
        if (stock < quantity) throw new IllegalStateException("재고 부족");
        this.stock -= quantity;
    }
}
```

```java
@Service
@RequiredArgsConstructor
public class OrderFacade {
    private final OrderService orderService;

    // 충돌하면 새 트랜잭션으로 최신 데이터를 다시 읽어 재시도한다.
    public void order(Long productId, int quantity) {
        for (int attempt = 1; ; attempt++) {
            try {
                orderService.order(productId, quantity); // @Transactional 메서드
                return;
            } catch (ObjectOptimisticLockingFailureException e) {
                if (attempt == 3) throw e; // 재시도 한도를 두고, 넘으면 사용자에게 알린다
            }
        }
    }
}
```

재시도 루프는 **트랜잭션 바깥**에 있어야 한다. 같은 트랜잭션 안에서 다시 시도하면 이미 읽어 둔 오래된 엔티티를 그대로 쓰게 된다.

### 비관적 락: `@Lock(PESSIMISTIC_WRITE)`

```java
public interface ProductRepository extends JpaRepository<Product, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
    @Query("select p from Product p where p.id = :id")
    Optional<Product> findByIdForUpdate(@Param("id") Long id);
}
```

```java
@Transactional
public void order(Long productId, int quantity) {
    Product product = productRepository.findByIdForUpdate(productId) // SELECT ... FOR UPDATE
            .orElseThrow();
    product.decrease(quantity);
} // 커밋 시 잠금 해제
```

잠금 타임아웃 힌트가 실제로 적용되는지, 어떤 SQL로 바뀌는지는 DBMS와 JPA 구현체(Hibernate의 방언)에 따라 다르다. 실제로 실행되는 SQL과 DB 설정(예: MySQL의 `innodb_lock_wait_timeout`)을 함께 확인하자.

## 언제 사용해야 할까?

| 기준 | 낙관적 락 | 비관적 락 |
| --- | --- | --- |
| 충돌 빈도 | 드물다 | 잦다 (인기 상품, 선착순) |
| 충돌 시 비용 | 재시도해도 괜찮다 | 실패하면 비싸다 (결제, 외부 호출 포함) |
| 대기 | 없음 | 잠금 대기 발생 |
| 처리량 | 높다 | 경합이 크면 낮아진다 |
| 교착 상태 | 발생하지 않음 | 가능성 있음 |
| 사용자 경험 | "다시 시도해 주세요" 처리 필요 | 느려질 수 있지만 순서대로 처리 |

- 게시글 수정, 설정 변경처럼 **동시에 같은 행을 수정하는 일이 드문** 경우 → 낙관적 락
- 재고 차감, 좌석 예약처럼 **같은 행에 요청이 몰리는** 경우 → 비관적 락을 고려하되, 잠금 범위와 트랜잭션을 짧게 유지
- 단순 증감이라면 `UPDATE product SET stock = stock - 3 WHERE id = 1 AND stock >= 3`처럼 **원자적 UPDATE 한 문장**으로 해결되는 경우도 많다.

## 주의 사항과 흔한 오해

- **"비관적 락을 걸면 다른 트랜잭션은 그 행을 읽을 수도 없다"** — 위에서 본 것처럼 DBMS와 격리 수준에 따라 다르다. MVCC 기반 DBMS의 일반 `SELECT`는 대개 막히지 않는다.
- **교착 상태(Deadlock)**: A는 행 1 → 행 2, B는 행 2 → 행 1 순서로 잠그면 서로를 영원히 기다릴 수 있다. DBMS가 감지해 한쪽을 롤백시키므로, **잠금 순서를 일정하게** 하고 롤백 시 재시도를 고려하자.
- **트랜잭션 안에서 외부 API를 호출하지 말자.** 비관적 락을 잡은 채로 느린 작업을 하면 다른 요청이 그만큼 대기한다.
- **낙관적 락은 버전이 바뀌는 수정만 보호한다.** JPQL 벌크 업데이트나 네이티브 쿼리처럼 영속성 컨텍스트를 거치지 않는 수정은 버전을 직접 올려야 한다.
- **`@Version`만 붙이고 예외 처리를 안 하면** 충돌 시 사용자는 500 에러를 보게 된다. 재시도 또는 409 Conflict 같은 명확한 응답을 설계하자.
- 서버가 여러 대여도 DB 락은 DB에서 동작하므로 유효하다. 반면 `synchronized` 같은 애플리케이션 락은 **한 JVM 안에서만** 동작한다.
