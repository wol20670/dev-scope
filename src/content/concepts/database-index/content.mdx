## 왜 필요한가?

회원이 1,000만 명인 `member` 테이블에서 이메일로 한 명을 찾는다고 해 보자.

```sql
SELECT * FROM member WHERE email = 'kim@example.com';
```

`email` 컬럼에 인덱스가 없다면 데이터베이스는 이 행이 어디 있는지 알 방법이 없다. 첫 행부터 마지막 행까지 **전부 읽으면서** 조건을 비교해야 한다. 이것을 **전체 테이블 스캔(Full Table Scan, PostgreSQL에서는 Seq Scan)** 이라고 한다. 찾는 행은 하나뿐인데 1,000만 행을 디스크나 메모리에서 읽어야 하고, 테이블이 커질수록 시간도 그에 비례해 늘어난다.

로그인, 주문 조회, 게시글 목록처럼 **같은 형태의 조회가 초당 수백 번** 일어나는 서비스라면 이 차이는 곧 응답 시간과 DB 서버 부하의 차이다. 인덱스는 "값으로 행의 위치를 빠르게 찾는" 별도의 자료구조를 유지해서 이 문제를 해결한다.

## 쉽게 이해하는 비유

**두꺼운 전공 책 뒤쪽의 색인(찾아보기)** 을 떠올려 보자.

- 색인이 없으면 "트랜잭션"이라는 단어가 나오는 쪽을 찾기 위해 책을 처음부터 끝까지 넘겨야 한다. → 전체 테이블 스캔
- 색인은 단어가 **가나다순으로 정렬**되어 있고, 각 단어 옆에 쪽 번호가 적혀 있다. 정렬되어 있으니 "ㅌ" 부분으로 바로 가서 단어를 찾고, 적힌 쪽으로 이동하면 된다. → 인덱스 탐색 후 테이블 접근
- 대신 책 내용이 바뀌면 색인도 고쳐야 하고, 색인 자체도 종이를 차지한다. → 쓰기 비용과 저장 공간

비유가 틀리는 지점도 있다. 책의 색인은 한 단계짜리 목록이지만, 실제 B-tree 인덱스는 "어느 범위의 값이 어느 페이지에 있는지"를 알려 주는 **여러 단계의 트리**다. 또 색인은 사람이 항상 쓰지만, DB 인덱스는 **옵티마이저가 쓰는 편이 더 싸다고 판단할 때만** 쓰인다.

## 동작 원리

### B-tree 인덱스

PostgreSQL과 MySQL(InnoDB) 모두 `CREATE INDEX`의 기본 인덱스 유형은 B-tree 계열이다. B-tree는 다음과 같은 성질을 가진 균형 트리다.

- **키가 정렬된 상태로 저장된다.** 그래서 `=` 비교뿐 아니라 범위 조건, `ORDER BY`에도 활용할 수 있다.
- **루트에서 모든 리프까지의 깊이가 같다(균형).** 한 노드(페이지)에 수백 개의 키가 들어가므로, 행이 수백만~수천만 개여도 트리 높이는 보통 몇 단계에 그친다.
- **리프 노드**에는 인덱스 키 값과, 실제 행을 가리키는 정보가 있다. 이 정보는 DBMS마다 다르다. PostgreSQL은 테이블(힙)에서 행의 물리적 위치(TID)를, MySQL InnoDB의 보조 인덱스는 **기본 키 값**을 저장한다. InnoDB 테이블 자체가 기본 키 순서로 정렬된 B-tree(클러스터형 인덱스)이기 때문이다.

조회는 루트에서 시작해 "찾는 값이 어느 자식 범위에 속하는가"를 비교하며 리프까지 내려간다. 비교 횟수는 행 수 n에 대해 대략 log n에 비례하므로, 행 수가 10배 늘어도 탐색 단계는 조금만 늘어난다. 전체 스캔이 n에 비례하는 것과 대조적이다.

### 인덱스를 쓴 조회의 두 단계

`SELECT * FROM member WHERE email = ?`에 인덱스를 쓰면 실제로는 두 단계가 일어난다.

1. **인덱스 탐색**: B-tree를 내려가 `email`이 일치하는 리프 항목을 찾는다.
2. **테이블 접근**: 리프에 적힌 위치(또는 기본 키)로 실제 행을 읽어 나머지 컬럼을 가져온다.

2단계는 행마다 **임의 위치 읽기(random access)** 가 될 수 있다. 결과 행이 몇 개라면 문제없지만, 조건에 맞는 행이 테이블의 상당 부분이라면 인덱스를 거쳐 행을 하나씩 찾아가는 것보다 **처음부터 순서대로 읽는 편이 더 빠를 수 있다**. 그래서 옵티마이저는 인덱스가 있어도 전체 스캔을 고르기도 한다. PostgreSQL은 그 중간 형태로, 인덱스에서 위치만 모은 뒤 물리적 순서로 정렬해 읽는 Bitmap Heap Scan도 사용한다.

### 선택도(Selectivity)

**선택도**는 조건이 전체 행 중 얼마나 적은 비율만 골라내는지를 말한다. 조건으로 걸러지는 행이 적을수록 "선택도가 높다"고 표현하며, 인덱스 효과가 크다.

- `email`, 주문 번호처럼 값이 거의 고유한 컬럼 → 한두 행만 골라내므로 인덱스 효과가 크다.
- `status`(값이 3~4종류), `is_deleted`(참/거짓)처럼 **값의 종류가 적은 컬럼** → 한 값이 테이블의 큰 비율을 차지하면 인덱스를 써도 이득이 작다.

옵티마이저는 테이블 통계(행 수, 값 분포 등)로 결과 행 수를 추정하고 비용을 비교한다. 통계가 오래되면 잘못된 계획을 고를 수 있으므로, PostgreSQL의 `ANALYZE`, MySQL의 `ANALYZE TABLE`로 통계를 갱신한다(대개 자동으로도 갱신된다).

### 복합 인덱스와 Leftmost Prefix

여러 컬럼으로 만든 **복합 인덱스(Composite Index)** 는 첫 번째 컬럼으로 정렬하고, 첫 번째 값이 같으면 두 번째 컬럼으로 정렬하는 식이다. 전화번호부가 "성 → 이름" 순으로 정렬된 것과 같다.

`(last_name, first_name)` 인덱스가 있을 때:

| 조건 | 인덱스로 범위를 좁힐 수 있나 |
| --- | --- |
| `last_name = '김'` | 가능 (선두 컬럼) |
| `last_name = '김' AND first_name = '민수'` | 가능 |
| `last_name = '김' AND first_name >= '마'` | 가능 (선두 등호 + 다음 컬럼 범위) |
| `first_name = '민수'` | 일반적으로 어렵다 (선두 컬럼 조건 없음) |

성 없이 이름만으로 전화번호부를 찾기 어려운 것처럼, **선두(가장 왼쪽) 컬럼에 조건이 없으면** 정렬 순서를 활용하기 어렵다. 이것을 **Leftmost Prefix 규칙**이라 부른다. PostgreSQL 문서도 복합 B-tree 인덱스는 선두 컬럼에 조건이 있을 때 가장 효율적이며, "선두 컬럼들의 등호 조건 + 그다음 첫 컬럼의 범위 조건"까지가 스캔 범위를 줄인다고 설명한다.

<Callout type="info" title="Skip Scan: 선두 컬럼 조건이 없어도 쓰는 경우">
PostgreSQL 18, MySQL 8.0.13 이상 등 일부 DBMS·버전은 **Skip Scan**으로 선두 컬럼 조건 없이도 복합 인덱스를 활용할 수 있다. 다만 선두 컬럼의 값 종류가 적을 때에만 효과적이고 적용 조건도 DBMS마다 다르다. 설계할 때는 Leftmost Prefix를 기본 원칙으로 삼고, 실제 사용 여부는 `EXPLAIN`으로 확인하자.
</Callout>

컬럼 순서를 정할 때는 보통 다음을 고려한다.

1. **항상 등호(`=`)로 조건이 걸리는 컬럼**을 앞에 둔다.
2. **범위 조건(`>`, `BETWEEN`, `LIKE 'abc%'`) 컬럼**은 그 뒤에 둔다. 범위 조건 뒤에 오는 컬럼은 스캔 범위를 줄이는 데 쓰이지 못하고, 걸러 내는 용도로만 쓰이는 경우가 많다.
3. `ORDER BY`까지 인덱스로 처리하려면 정렬 컬럼 순서도 맞춘다.

### 커버링 인덱스(Covering Index)

쿼리가 필요로 하는 컬럼이 **모두 인덱스 안에 있다면** 2단계(테이블 접근)를 생략할 수 있다. 이런 인덱스를 커버링 인덱스라 한다.

- MySQL `EXPLAIN`의 `Extra` 열에 `Using index`가 보이면 인덱스만으로 처리했다는 뜻이다.
- PostgreSQL에서는 **Index Only Scan**으로 나타난다. 단, PostgreSQL 인덱스에는 행 가시성(MVCC) 정보가 없어서, 해당 페이지가 "모두 보이는 상태"인지 visibility map으로 확인하고 그렇지 않으면 결국 테이블을 읽는다. 자주 변경되는 테이블에서는 기대만큼 효과가 없을 수 있다.
- PostgreSQL은 `INCLUDE` 절로 검색 키는 아니지만 함께 저장할 컬럼을 지정할 수 있다.

### 쓰기 비용

인덱스는 공짜가 아니다.

- **INSERT/DELETE**: 테이블뿐 아니라 그 테이블의 **모든 인덱스**에도 항목을 추가·삭제해야 한다.
- **UPDATE**: 인덱스에 포함된 컬럼을 바꾸면 인덱스 항목도 바뀐다. 실제로 어떤 경우에 인덱스 갱신이 일어나는지는 DBMS 구현에 따라 다르다(예: PostgreSQL은 인덱스 컬럼이 바뀌지 않는 일부 갱신을 HOT update로 최적화한다).
- **저장 공간**: 인덱스는 별도 공간을 차지하고, 메모리(버퍼 캐시)도 테이블과 나눠 쓴다.

그래서 "일단 다 걸어 두자"가 아니라 **실제로 자주 실행되는 쿼리**를 기준으로 인덱스를 설계한다.

### 인덱스가 있어도 쓰이지 않는 경우

인덱스는 "컬럼 값 그대로" 정렬되어 있다. 조건이 그 정렬 순서를 활용할 수 없는 형태면 인덱스로 범위를 좁힐 수 없다. 대표적인 예는 다음과 같다(정확한 동작은 DBMS와 버전에 따라 다르다).

- **컬럼에 함수나 연산을 적용**: `WHERE DATE(created_at) = '2026-11-19'`, `WHERE price * 1.1 > 1000`. 인덱스에는 `created_at` 원래 값이 정렬되어 있지 `DATE(created_at)` 결과가 정렬되어 있지 않다. 범위 조건으로 바꾸거나, 표현식 인덱스(PostgreSQL)·함수 기반 키 파트(MySQL 8.0.13 이상)를 만든다.
- **앞쪽 와일드카드 `LIKE`**: `LIKE 'kim%'`처럼 접두사가 고정되면 범위 탐색이 가능하지만, `LIKE '%kim'`이나 `LIKE '%kim%'`은 시작 위치를 알 수 없어 B-tree로 범위를 좁힐 수 없다. PostgreSQL에서는 C 로케일이 아니면 접두사 `LIKE`에도 `text_pattern_ops` 같은 별도 연산자 클래스가 필요할 수 있다.
- **타입 변환**: MySQL에서 문자열 컬럼을 숫자와 비교(`WHERE phone = 01012345678`)하면 `'010...'`, `'10...'` 등 여러 문자열이 같은 숫자로 변환될 수 있어 인덱스를 쓰지 못한다. 컬럼 타입과 같은 타입의 값을 바인딩하자.
- **결과 행이 너무 많을 때**: 위에서 본 것처럼 옵티마이저가 전체 스캔이 더 싸다고 판단하면 쓰지 않는다. 이것은 문제가 아니라 올바른 판단일 수 있다.
- **선두 컬럼 조건이 없는 복합 인덱스**, **`OR`로 묶인 서로 다른 컬럼 조건** 등도 인덱스를 제대로 활용하지 못하는 흔한 원인이다.

## 코드 예시

### 인덱스 만들기와 실행 계획 확인 (PostgreSQL)

```sql
CREATE TABLE orders (
    id          bigserial PRIMARY KEY,
    member_id   bigint      NOT NULL,
    status      varchar(20) NOT NULL,
    total_price integer     NOT NULL,
    created_at  timestamptz NOT NULL DEFAULT now()
);

-- "회원의 최근 주문 목록" 조회를 위한 복합 인덱스
CREATE INDEX idx_orders_member_created ON orders (member_id, created_at);

-- 실행 계획만 확인 (쿼리를 실행하지 않는다)
EXPLAIN
SELECT id, status, total_price
  FROM orders
 WHERE member_id = 42
 ORDER BY created_at DESC
 LIMIT 20;
```

출력 예시는 다음과 같은 모양이다(비용·행 수는 데이터에 따라 다르다).

```sql
-- Limit  (cost=0.43..80.12 rows=20 width=26)
--   ->  Index Scan Backward using idx_orders_member_created on orders  (cost=0.43..1210.55 rows=304 width=26)
--         Index Cond: (member_id = 42)
```

- `Seq Scan on orders`가 보이면 전체 스캔이다.
- `Index Scan`, `Index Only Scan`, `Bitmap Heap Scan`은 인덱스를 사용한 계획이다.
- `Backward`는 인덱스를 역순으로 읽어 `ORDER BY ... DESC`를 별도 정렬 없이 처리했다는 뜻이다.

`EXPLAIN ANALYZE`는 **쿼리를 실제로 실행**하고 추정치와 실제 행 수·시간을 함께 보여 준다. `UPDATE`/`DELETE`에 쓸 때는 트랜잭션으로 감싸 롤백하자.

```sql
BEGIN;
EXPLAIN ANALYZE UPDATE orders SET status = 'CANCELED' WHERE member_id = 42;
ROLLBACK;
```

### 커버링 인덱스

```sql
-- PostgreSQL: 검색 키는 member_id, created_at이고 status, total_price는 함께 저장만 한다
CREATE INDEX idx_orders_member_created_cover
    ON orders (member_id, created_at) INCLUDE (status, total_price);
```

위의 조회는 이제 테이블을 읽지 않는 `Index Only Scan`이 될 수 있다(visibility map 상태에 따라 실제 테이블 접근 여부는 달라진다).

### 인덱스를 못 쓰는 조건 고치기

```sql
-- 인덱스 컬럼에 함수를 적용: created_at 인덱스로 범위를 좁히기 어렵다
SELECT * FROM orders WHERE date(created_at) = '2026-11-19';

-- 범위 조건으로 바꾸면 created_at 정렬 순서를 그대로 활용할 수 있다
SELECT * FROM orders
 WHERE created_at >= '2026-11-19'
   AND created_at <  '2026-11-20';
```

```sql
-- 대소문자 무시 검색이 꼭 필요하다면 표현식 인덱스를 만든다 (PostgreSQL)
CREATE INDEX idx_member_lower_email ON member (lower(email));

SELECT * FROM member WHERE lower(email) = 'kim@example.com';
```

### MySQL에서 확인하기

```sql
CREATE INDEX idx_orders_member_created ON orders (member_id, created_at);

EXPLAIN
SELECT id, created_at
  FROM orders
 WHERE member_id = 42
 ORDER BY created_at DESC;
```

MySQL `EXPLAIN` 결과에서는 다음 열을 주로 본다.

- `type`: `ALL`이면 전체 스캔, `ref`·`range`·`const` 등은 인덱스 접근이다.
- `key`: 실제로 선택된 인덱스 이름. `NULL`이면 인덱스를 쓰지 않았다.
- `rows`: 옵티마이저가 추정한 검사 행 수.
- `Extra`: `Using index`는 커버링 인덱스, `Using filesort`는 인덱스로 정렬하지 못해 별도 정렬을 했다는 뜻이다.

InnoDB 보조 인덱스에는 기본 키 값이 함께 들어 있으므로, 위 쿼리의 `id`(기본 키)와 `created_at`은 인덱스만으로 얻을 수 있다.

## 언제 사용해야 할까?

| 상황 | 인덱스 효과 |
| --- | --- |
| `WHERE`, `JOIN`에 자주 쓰이고 값이 다양한 컬럼 (이메일, 외래 키, 주문 번호) | 크다 |
| 큰 테이블에서 소수의 행만 조회 | 크다 |
| `ORDER BY ... LIMIT`처럼 정렬된 일부만 필요 | 정렬까지 인덱스로 처리 가능 |
| 값의 종류가 적고 한 값이 대부분을 차지하는 컬럼 (`is_deleted`) | 작다 (단, 드문 값만 조회한다면 효과가 있을 수 있다) |
| 작은 테이블, 대부분의 행을 읽는 집계·리포트 쿼리 | 작다 |
| 쓰기가 매우 잦고 조회는 드문 테이블 (로그 적재) | 쓰기 비용이 더 클 수 있다 |

설계 순서는 대략 다음과 같다.

1. 느린 쿼리 로그나 APM에서 **실제로 자주·느리게 실행되는 쿼리**를 찾는다.
2. `EXPLAIN`(필요하면 `EXPLAIN ANALYZE`)으로 현재 실행 계획을 확인한다.
3. 조건과 정렬을 보고 인덱스(컬럼 순서 포함)를 설계한다. 기존 인덱스의 컬럼 순서만 바꿔 해결되는지도 본다.
4. 다시 `EXPLAIN`으로 계획이 바뀌었는지, 실제 시간이 줄었는지 확인한다.
5. 사용되지 않는 인덱스는 쓰기 비용만 늘리므로 주기적으로 정리한다.

외래 키 컬럼은 JOIN과 연관 엔티티 조회(예: JPA의 `member_id`로 주문 목록 조회)에 자주 쓰인다. MySQL InnoDB는 외래 키 제약을 만들 때 인덱스를 요구하지만, PostgreSQL은 참조하는 쪽 컬럼에 인덱스를 자동으로 만들지 않으므로 직접 만들어야 한다.

## 주의 사항과 흔한 오해

- **"인덱스를 만들면 그 컬럼 조회는 항상 빨라진다"** — 옵티마이저는 비용을 비교해 인덱스를 쓰지 않을 수도 있고, 결과 행이 많으면 실제로 전체 스캔이 더 빠를 수 있다. 판단 근거는 추측이 아니라 `EXPLAIN` 결과다.
- **"인덱스는 많을수록 좋다"** — 모든 인덱스는 쓰기마다 함께 갱신되고 공간과 메모리를 차지한다. 비슷한 인덱스가 여럿이면 하나로 합칠 수 있는지 보자. 예를 들어 `(a)`와 `(a, b)`가 있다면 `(a)`는 대개 `(a, b)`로 대체된다.
- **"복합 인덱스는 컬럼 순서가 상관없다"** — 정렬은 선두 컬럼부터 이루어진다. `(member_id, created_at)`과 `(created_at, member_id)`는 전혀 다른 쿼리에 유리하다.
- **"`WHERE` 절에 인덱스 컬럼이 있으면 인덱스를 쓴다"** — 컬럼에 함수를 씌우거나, 앞쪽 와일드카드 `LIKE`를 쓰거나, 타입이 다른 값과 비교하면 인덱스로 범위를 좁히지 못할 수 있다. 정확한 조건은 DBMS와 버전에 따라 다르므로 실행 계획으로 확인하자.
- **`EXPLAIN ANALYZE`는 쿼리를 실제로 실행한다.** 운영 DB에서 데이터 변경 쿼리에 그대로 쓰면 데이터가 바뀐다.
- **개발 DB에서 빠르다고 운영에서도 빠른 것은 아니다.** 데이터가 100건일 때는 어떤 계획이든 빠르다. 실행 계획은 데이터 양과 분포, 통계에 따라 달라지므로 운영과 비슷한 규모로 확인해야 한다.
- **인덱스가 N+1 문제를 해결해 주지는 않는다.** 쿼리 한 번은 빨라지지만 쿼리 횟수 자체가 많은 문제는 페치 조인 등으로 따로 해결해야 한다.
